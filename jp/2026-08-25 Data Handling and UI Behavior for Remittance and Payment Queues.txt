📒Meeting Outline

Data Handling and UI Behavior for Remittance and Payment Queues

• Sequence Number and Primary Key Usage  
  The sequence number is an editable field and not shown in the UI for BAU (Business As Usual) or uplift versions. It is not required to be displayed on the UI. Instead, the remittance ID serves as a unique primary key for the remittance table. The current BAU approach does not pass the primary key back to the UI; the UI holds the entire data set even when modifying payments. The team discussed aligning Pilot 2 and Pilot 3 with this logic but noted challenges with pagination and data handling.

• UI Data Submission and Staging Table Usage  
  The UI is expected to send the entire data set back after user modifications. To support multiple edits before submission, all data is loaded into a staging table, where modifications, deletions, and additions are applied before final submission. There is a hard limit on the number of records shown in the UI drawer (initially 1000, considered to be increased). For Pilot 3, a more scalable solution is needed due to expected higher data volumes.

• Handling Large Data Volumes and Hybrid Approach  
  For large remittance counts, a hybrid approach is proposed where the backend reads modified remittance data from the staging table instead of relying solely on UI payloads. This reduces UI bottlenecks and improves performance. This approach will be evaluated after Pilot 1 completion.

• Batch Processing and Modify Batch Functionality  
  Modify Batch currently handles one recipient at a time, allowing deletion or editing of recipients in the payment queue. Similar logic and functions need to be applied to the remittance queue for add, modify, edit, and delete actions. The sequence number is not significant for these operations and can be removed to avoid complications.

• Type Field and User Interaction  
  The 'type' field drives the state of remittance entries (change, old, delete, new). User edits should not immediately remove old entries until submission, allowing cancellation without data loss. This behavior needs to be carefully managed to avoid premature data removal.

Deployment and Pilot Progress

• Pilot 1 and Pilot 2 Status  
  Pilot 1 clients (from the US) are using the batch functionality. For Pilot 2 (India), batch processing is currently not included as per recent decisions. The backend code is ready, and UI code has been deployed to QA3 but is experiencing slowness. Deployment timing is uncertain.

• Cascading Effects on Other Teams and Features  
  Omar's team is waiting for deployment to proceed with batching QA and to merge PRs for SEPA credit and other features like Swiss payments. Delays in deployment will cause a domino effect impacting these related projects.
