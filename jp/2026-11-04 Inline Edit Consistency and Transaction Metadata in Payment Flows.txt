📒Meeting Outline

Inline Edit / Modify Flow Consistency (Payments & Templates)

• Inline edit response vs drawer (modify) response
  The group discussed keeping the inline-edit response consistent with the modify-drawer response so the UI can reuse the same field-key / value mapping when building the final submit payload. Backend responses for inline-edit currently include a set of fields; the proposal is to ensure the inline response returns the same applicable field metadata (field key like PMT_xxx and values) as returned for drawer/modify flows so UI does not need extra filtering or special logic. There is debate: some prefer returning minimal fields (only non-empty) while others prefer returning the full set of applicable fields (including empty values) for consistency with existing UI behavior.

• Empty-value fields in payloads
  There was a clear difference of opinion: one side argues it’s acceptable and simpler to exclude fields with empty values (minimal payload), while the other insists on including fields with empty values to avoid changing UI logic and to keep identification of applicable fields consistent. The team recognized that including empty keys typically has no negative persistence impact but avoids extra UI logic.

• Action: try initial experiment
  Consensus: For a first iteration, let the UI take whatever inline-edit response is produced and attempt constructing and submitting a payload to validate whether excluding empty fields causes issues. If issues appear, adapt to return the consistent set including empty keys.

Transaction / Transmitter Metadata (submit payloads)

• Transmitter data necessity and origin
  Transaction metadata (transmitter data) required for final modify-submit (action, amount, transactionId, version) must be present in the submit payload. For modify flows the UI currently constructs transmitter data using fields coming from backend responses (e.g., beneficiary list provides version/transaction details). For inline-edit, the UI sometimes lacks the same object context and thus must either build the transmitter metadata itself or get it returned in the inline-edit response.

• Version importance
  The version field (transaction version) is required by backend to apply a modification; it must be taken from backend responses (getBeneficiaryList or equivalent) and echoed back in submit. Version is not a UI-generated increment—it must reflect backend-provided value.

• Where transmitter data is built
  Clarified: UI builds transmitter data using information returned from backend responses. For inline edits, either UI must construct it (if it has necessary info) or backend must include the necessary metadata in the inline response so UI can forward it back (unchanged) to the submit API.

• Decision/next step
  Short-term: UI will try to build the transmitter metadata from the inline response and use it in submit. Team will confirm if inline response must be enriched with transmitter fields. Kumar and Kuber to discuss details separately (avoid spending more meeting time).

Allow-Edit Flag (Templates -> Payment behavior and UI)

• Requirement
  When creating a payment from a template (or when a payment is created from template and later modified), each recipient’s instructed amount field needs an editable flag indicating whether the inline amount field should be editable on the payment queue grid and in the drawer. The flag should be present in responses driving the payment grid and the modify flows.

• Where to add flag
  Agreement to expose a boolean flag (name to be agreed) inside instructedAmount (or the instructedAmount block) in the getBeneficiaryList / beneficiary responses. This flag will be used by the UI to render the amount field as editable/non-editable in payment queue and modify drawer flows. For payments created from templates, the flag must persist so that subsequent modify flows know which rows are editable.

• Flag semantics & defaults
  Recommendation: default behavior is false (not editable) unless explicitly set true for the specific recipient created from template. The team discussed whether to omit the flag when not applicable versus always sending it with default false; leaning toward including it but setting default false to avoid omissions.

• Scope
  Allow-edit applies only to fields configured in DB (not to every field universally). Initially required for instructedAmount (amount) on payment queue and modify flows; extendable later to other fields as configured.

• Template modify flow vs payment-from-template
  Clarified difference:
  • Modifying template definition (template editor) is separate; allow-edit configuration exists as template metadata and may be toggled there.
  • Payment created from a template should inherit the recipient-level allow-edit setting from the template so the payment grid/drawer reflect that setting.
  • When template allow-edit toggles after a payment was created, clarify desired behavior — currently discussion focused on payments created from templates and modify flows using the inherited flag.

• Implementation notes
  The flag will be added to getBeneficiaryList responses (and related APIs that feed the grid). The drawer/modify response (modify payment in batch) must also provide this metadata so UI shows identical toggle behavior.
