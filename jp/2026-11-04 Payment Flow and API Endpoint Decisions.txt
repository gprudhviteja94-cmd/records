📒Meeting Outline

Create Payment From Template — API flow and endpoint decision

• Use-case clarification
  Discussion focused on the "create payment from template" flow where a user edits a recipient (Benny) from a batch template. The core question: should the backend call modifyBennyInBatchTemplate or modifyPaymentInBatch for the drawer edit flow? Participants agreed the flow is functionally a payment flow (not a template edit) once the user proceeds to create a payment.

• Final endpoint decision
  Consensus: use modifyPaymentInBatch (payment endpoint) for the drawer edit in create-payment-from-template. The payment endpoint will be adapted to accept template-origin inputs and respond with a payment-style response so UI contract remains consistent.

• Flag to indicate source
  Introduce a boolean flag isPaymentFromTemplate in the modifyPaymentInBatch request. When true, backend switches data-source and response generation to treat incoming IDs as coming from template constructs (templateId and templateBennyId) and to produce payment-formatted response.

• Payload mapping and parameters
  For payment-from-template requests the payload must include:
  • templateId (batch template id)
  • templateBennyId (recipient / Benny id in template)
  • isPaymentFromTemplate: true
  • valueDate (discussed — see below)
  • other create/payment fields as usual (amount input, debit account, clearing system etc.)
  Do not repurpose existing transactionId/paymentTransactionBatchId fields to carry template IDs (team prefers explicit new fields rather than overloading transaction fields).

Response shape, fields to suppress and transformations

• Suppress template-only fields
  When isPaymentFromTemplate = true, the response must NOT include template-only controls such as:
  • allowEdit checkbox (do not return these fields at all)
  • maximumPaymentAmount (suppress unless needed to show as helper text — see below)
  The UI should not receive allow edit settings as a visible checkbox for payment flows.

• Editable flags mapped to payment response
  The backend must convert template allow-edit configuration into payment-response editable metadata:
  • For fields that are not allowed to be edited (allowEdit=false in template), return the corresponding field in the payment response with editable: false (or equivalent) so the UI can render it disabled/greyed-out in the drawer.
  • Default amounts in templates should map to payment amount field. If template had default amount, show that in the amount field; if not, the field is blank.

• Maximum amount display
  If a templateBenny has a maximumPaymentAmount configured, the response should include that information in a form consumable by UI (as helper text under the amount field). The team will validate this by verifying single-template → payment-from-template behavior.

• Response contract consistency
  The payment response contract must remain the same as standard modifyPaymentInBatch response. Internally data may be sourced from template Benny tables, but the outward response must look like a payment response (with editable flags set appropriately and template-only fields omitted).

• Transform/synthesizer logic
  Backend will implement a synthesizer/converter that:
  • reads from templateBenny / template tables when isPaymentFromTemplate is true,
  • converts that data into the payment view model (payment synthesizer),
  • applies allow-edit rules to set editable flags and hide template-only fields,
  • returns the payment-style response to UI.
  This synthesizer can reuse existing mappers where possible; post-processing will adjust metadata (templateId, templateBennyId) as required.

Data source and implementation details

• Where data comes from
  • Template data exists in templateBenny and template tables. When isPaymentFromTemplate flag is on, modifyPaymentInBatch should fetch from templateBenny and feed the data into the payment synthesizer.
  • For normal payment flows, data is read from payment transaction tables as before.

• Value date handling
  Value date is not present in template records. In create-payment-from-template flow:
  • UI generally selects valueDate on the main page before opening drawer.
  • The backend may accept valueDate in the modifyPaymentInBatch request (recommended) so the response can include the valueDate for the drawer.
  • Team concluded: include valueDate in the request payload and return/display consistently (do not add complex formatting logic in this change).

• Request/response fields and backward-compatibility
  • New request will include extra fields (templateId, templateBennyId, isPaymentFromTemplate). This is additive and should not break existing clients.
  • Avoid repurposing existing transaction or batch id fields to hold template IDs; use explicit fields.

• Code structure and reuse
  • Reuse the existing payment response mappers and view synthesizers as much as possible.
  • Implement a modular method for converting templateBenny -> payment view (post-processing method / buildTranMetadata or similar).
  • Reuse existing getTemplateDetails method flow where feasible; add a wrapper that calls the existing compose/mapper methods and then post-processes for Benny/template specifics.

Miscellaneous technical clarifications

• Why modifyPaymentInBatch
  • Because once the user starts creating a payment it is considered a payment flow; UI and downstream flows expect payment-like responses and behavior (no allow-edits checkbox).
  • Using the payment endpoint avoids UI contract changes and keeps drawer rendering consistent.

• Edge cases
  • Make sure templateBenny editable configuration is applied field-wise (per recipient/line) so some fields can be editable and others not.
  • Confirm maximum amount rendering in payment-from-template case by testing a template with max amount set.
