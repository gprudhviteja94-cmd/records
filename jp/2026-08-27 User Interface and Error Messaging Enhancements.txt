📒Meeting Outline

User Interface and Error Messaging Updates

• Confluence Documentation and Error Messaging  
  Armando updated the Confluence page to include new error messaging screenshots with backgrounds for clarity. Some outdated screenshots and references related to the drawer-level display were deleted as the drawer-level error messaging was decided to be skipped.

• Cancel and Close Button Behavior  
  Discussion clarified that the "X" close button returns users to the original modifier create payment screen without saving changes, allowing users to modify or save later. The "Cancel this transaction" button cancels the creation process and returns users to the payment activity grid, discarding unsaved data. This behavior is consistent with existing BAU processes and applies to both batch and single payments. It was noted that cancel is not a status progression but a user action to abort creation or modification.

• Cutoff Messaging and Options  
  The system currently only supports a hard cutoff (post cutoff) without a separate best cutoff option. After the cutoff threshold, users are offered to make changes for the next valid business day. The messaging and UI for this process were discussed as somewhat confusing, with suggestions to simplify the instructions and reduce unnecessary clicks. Armando will consult with the DXD team about potential improvements.

• Banner Background Consistency  
  A question was raised about the inconsistent use of red background versus transparent background for mandatory banners across different screens (e.g., account transfer). Armando will review Figma designs and confirm the consistent approach for these banners.

Pagination and Remittance Line Addition

• Pagination Starting Point and Behavior  
  Currently, pagination starts at 10 items per page, but production uses 100 items per page. The team agreed to align with production and start pagination at 100. A key issue was identified where adding a new remittance line at the page limit does not automatically navigate the user to the next page, causing confusion. The expected behavior is that after adding the 100th item, the UI should automatically move to the next page to allow continuous addition.

• Add New Line Button vs Plus Icon  
  For creation flows, a fixed "Add New" button is preferred over a plus icon embedded in the list, as it simplifies adding new lines, especially when pagination is involved. For modification flows with many remittance lines (e.g., 500+), the plus button appears only on the last page. The team discussed possibly mimicking the production approach with a fixed add new line input for better usability.

• Testing and Validation  
  Armando will test the current behavior in the dev environment to confirm how pagination and line addition behave during modification flows and consider improvements if the current behavior is suboptimal.

Batch Payment Track and Trace Functionality

• Batch Level Status and Individual Transaction Statuses  
  The track and trace feature shows the overall batch status at the top and individual transaction statuses in a grid below. The batch status reflects the progress (e.g., submitted, approved, delivered), while individual transactions have their own statuses. The final batch status (e.g., delivered) indicates completion at the batch level.

• UI Display and Status Terminology  
  There was discussion about how to represent multiple statuses at the batch level, with concerns about showing "complete" when some transactions may have issues. The use of "multiple" as a status was considered to avoid confusion. Armando will review the Figma designs created by Pranima and coordinate with her to finalize the UI and status handling.

• Viewing Individual Transactions  
  Clicking on the batch status should open a detailed view (drawer or separate screen) showing individual transaction statuses. This functionality is under development.

Data Display and Batch Import Details

• Handling Multiple Values in Batch Columns  
  For batch payments, some columns such as "approved by" or "beneficiary address" are blank or show inconsistent data. The team discussed using the word "multiple" in these fields when multiple values exist, consistent with ITC practices.

• Data Migration and Automation  
  Santhosh mentioned ongoing work related to data migration and automation for batch processing, including handling large data sets (e.g., 800,000 records). He offered to share relevant tables and details with the team.

Toggle for Batch Creation Option

• Toggle to Enable Batch Payment Creation  
  There will be a toggle feature to enable or disable batch payment creation for clients. Without the toggle, users can only create single payments. This toggle is not yet visible in the dev environment but is expected to be available soon. Armando will confirm the status and coordinate with the team.

Navigation and UI Adjustments

• Screen Navigation and Layout Updates  
  Armando updated navigation screens to remove brand elements and simplify display fields such as constructed amount, recipient account number, and recipient name. Some UI elements like the range and status fields still have appearance issues that need fixing.

• Next Steps for UI and Development  
  Armando plans to share AI-generated notes and continue working on remittance design and other UI improvements.
