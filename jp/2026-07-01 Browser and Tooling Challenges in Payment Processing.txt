Browser and Tooling Issues

Payment Transaction and Staging Data Flow

• Understanding Modify Payment Wrapper and Scenarios  
  Discussion focused on the modify payment wrapper API, its interaction with payment transaction tables and staging tables. The wrapper is designed to handle both create batch and modify batch scenarios, with different request parameters depending on whether data exists in staging or only in payment transaction tables.

• Create Batch Scenario  
  In the create batch flow, data exists only in staging tables (no entries yet in payment transaction tables). The challenge is to convert staging data into a payment transaction object that can be used to generate the expected structured response for the UI.

• Modify Batch Scenario  
  For modify batch, the batch and transaction already exist in payment transaction tables. The user modifies recipient data, which is saved into staging tables. When the user re-opens the modify drawer, the wrapper should overlay staging data on top of payment transaction data to present the latest modified values.

• Request and Response Structure  
  The modify payment wrapper currently calls existing BAU modify payment endpoints to fetch data from payment transaction tables and then overlays staging data using a static mapper. The response structure must match the existing modify payment output format, including sections and fields for UI rendering.

Data Mapping and Reverse Mapping Logic

• Static Mapper vs Reverse Mapper  
  The current overlay uses a static mapper to update values after fetching the structured response from the modify payment API. However, it was suggested to leverage the existing reverse mapper logic that converts payment transaction objects into the structured response format. This approach would be more maintainable and consistent, especially across different pay methods and use cases.

• Reverse Mapper Importance  
  Reverse mapper applies complex logic based on driver fields (e.g., pay method, recipient country, currency) to generate the correct response structure. Using it would avoid maintaining separate static mapping logic and ensure consistency with existing flows.

• Implementation Approach  
  The recommended approach is to:
  1. Query the payment transaction object from the database (or create it from staging data in create batch scenario).
  2. Overlay staging data on this object.
  3. Use the reverse mapper to generate the final structured response for the UI.

Challenges and Next Steps

• Data Volume and Performance Concerns  
  Large JSON responses cause browser crashes, complicating debugging. There is a need to optimize how data is fetched and presented.

• Clarification on APIs and Data Flow  
  Some confusion exists regarding which APIs are used for saving and fetching staging data, and which are used for final submission. It was clarified that staging APIs save data temporarily, and final submission updates payment transaction tables.

• Action Plan

  • Investigating existing modify payment flow code.
  • Creating payment transaction objects from staging data.
  • Applying reverse mapping to generate UI-ready responses.
  • Ensuring driver fields are included in requests for correct mapping.
