📒Meeting Outline

Payment Rate Handling and Contract Booking

• The discussion clarified that the indicative rate shown to users is not sent during the submit phase, and the visible rate scenario differs from the indicative rate scenario.  
• At release time, the actual rate is accepted, not the indicative rate. The visible rate is triggered only if the rate type 004 is sent during submit.  
• Without sending rate type 004, the visible rate will not be triggered, and the backend does not currently send this rate type in the submit call, which is identified as an issue.  
• The rate type 4 is crucial as it determines whether an XSFX API call is made to get the visible rate, which may be treated as an auto effect.  
• It was noted that this behavior applies across all rate types, and the contract booking depends on sending the correct rate type.  

Payment Queue and Payment Grid Field Display and Labeling

• There is a discrepancy between the payment queue and payment grid in how the "from account" or "ordering account" is displayed.  
• The user preference controls whether the account number or account name is shown, and this preference should be respected in the payment queue display, specifically for the ordering account column.  
• It was agreed that the payment queue should render only the account number, applying user preferences such as suppressing leading zeros.  
• Label changes were confirmed:  
  • "Ordering originating account" replaces "from account number"  
  • "Instructed amount" is preferred over "payment amount" or "receipt amount" for clarity and consistency with the payment activity grid.  
• For currency and recipient account fields, the label should reflect either recipient or debit account number depending on the transaction type (ACCR or ACSDR).  
• The column header will remain "recipient/debit account" without "number" to keep the label concise.  
• Bank ID labeling will be standardized as "bank ID" to avoid confusion with ID type fields.  
• Four label changes were identified and will be communicated to the team.  

Validation and Pre-Validation Workflow in Payment Batch Creation and Modification

• The current workflow includes pre-validate calls and validation calls during drawer operations (create or modify batch).  
• It was proposed that validation errors during pre-validate in the drawer should be ignored to allow users to save and close or save and add another without interruption.  
• The final validation, including value date validation, should occur only at the submit level.  
• A pop-up will appear on submit if there is a value date error, directing the user to update the value date field.  
• The value date field is not present on the payment queue page but on a previous page, which complicates immediate correction during submit.  
• The team agreed to remove validate and cutoff validations from subsequent pre-validate calls after the first one, but the initial pre-validate call remains necessary.  
• There was discussion about whether to handle ignoring errors at the UI or backend level; the consensus leaned towards ignoring validation errors on the UI during drawer operations.  
• Pre-validate calls happen regardless of whether the user intends to save or submit, so ignoring errors during pre-validate for drawer saves is important to avoid blocking user actions.  
• The create batch process may have cutoff validations that should stop the process and prompt the user accordingly.  

📋Overview

• The indicative rate is only for display and not sent during submit; sending rate type 004 is essential to trigger visible rate and proper contract booking.  
• Payment queue display should respect user preferences for showing account number or name, with agreed label changes for clarity and consistency with the payment activity grid.  
• Validation errors during drawer pre-validation should be ignored to allow saving actions, with full validation deferred to the submit stage.  
• Value date errors will trigger a pop-up on submit, guiding users to correct the field on the relevant page.  
• Labeling and field naming conventions were standardized to maintain consistency across grids and queues.
