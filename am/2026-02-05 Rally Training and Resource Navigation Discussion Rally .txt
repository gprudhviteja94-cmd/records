Rally data model: people, time, work (three dimensions)

  • People (teams and project spaces)
    Rally organizes people as teams and team hierarchies. Workspaces/project spaces often reflect teams. Naming conventions were explained: project spaces beginning with "E_" indicate execution-level teams; "S_" indicates strategy-level spaces (groups of teams, release trains, program/product groups). Guidance on scoping: using parent/child project checkboxes affects which data is shown. Recommended default: uncheck parent projects and leave child projects checked to avoid confusing cross-scope results.

  • Time (iterations, program increments/releases, milestones)
    Time in Rally is represented by:
    
    • Iterations (sprints): typically 10 working days (2-week cadence).
    • Program increments (PIs) / releases: a collection of iterations (commonly 5 iterations).
    • Milestones: date-based groupings for one-off targets (e.g., deployments, trade shows).
      American Express uses a common PI calendar; iterations and PIs are synchronized across teams. The principle emphasized: “develop on a cadence, deliver on demand.”

  • Work (work item hierarchy)
    Work items are hierarchical:
    
    • Epic: large initiatives (often >1 year)
    • Capability: multi-PI work (typically >6 months and <1 year)
    • Feature: fits within one PI (≈10 weeks)
    • User Story: deliverable within one iteration
    • Tasks: sub-day work items contributing to a story
      The presenter explained parent-child relationships and the expected time horizons for each level.


Access, permissions, and searching for items

  • Search limitations due to access
    A user (Aparna) could not find a capability via the top search bar; the instructor explained that missing results often mean the user lacks access to the project space containing that item. The Rally self-service page (project/ID lookup) was demonstrated as an alternative to find items or confirm IDs. If the search still fails, permissions or scoping are likely the issue.

  • Permissions and next steps for access
    To get access beyond the default Rally project space, users must request access to specific project spaces. Typical contacts to resolve access: Agile champion, release train engineer (RTE), or project admins. The presenter noted that Rally provisioning uses email addresses and that sometimes issues are related to the user’s ID or provisioning; they offered to check the attendee’s (Aparna’s) Rally email provisioning status.


Q&A examples and guidance workflow

  • Example troubleshooting flow
    1. User can’t find an item via search → likely lack of access.
    2. Use Rally self-service page to search by ID or project.
    3. If ID is not accessible, contact Agile coach/Agile champion/RTE or submit an IT/IIQ access request.
    4. If provisioning issues persist, escalate to Rally support via the self-service support link or Slack channels.


📋Overview

  • Training content is centralized and filterable; “Access and Navigation” is the recommended starting video.

  • Rally models data across three dimensions: people (teams), time (iterations/PI/milestones), and work (epics → capabilities → features → stories → tasks).

  • Provisioning in Rally is email-based; ID/email provisioning is a common source of access problems.
