Data Migration and Environment Setup for DQ Artifacts

• Data migration to Lumi and environment challenges  
  With the self-sub-UI, data is migrating to Lumi, and the platform will run in the production environment. There is a need to create a Lumi ingestion pipeline for the DQ artifacts table. However, updating or creating SQL files for new rules ideally should happen in the dev environment, but there are challenges in fetching the warehouse data and mapping production profiles to test profiles.

• Profiles and environment mapping issues  
  Production profiles in SFP cannot be mapped to test profiles in Lumi, making it impossible to create certain mappings in the test environment. A workaround suggested is to store results in a test table and, after UAT sign-off, dump data into the DQ repository. However, this approach limits scope for code changes.

• RFC and UAT challenges  
  Raising RFCs requires details of the E2 environment, which is complicated by the tool being in an early feature stage with uncertain accuracy. Disturbing the production environment is a concern, so feasibility checks are ongoing.

DQ Rules Migration and Execution

• Creation of entries for all check types  
  Entries were created for four DQ check types: duplicate check, threshold check, value check, and missing value check. The table used is a clone of the DQ Artifacts table from SFT, ensuring schema consistency.

• Threshold check exclusion  
  Threshold check will be excluded from the next run as it will be handled via control, allowing focus on the other three check types.

• Execution and output generation  
  The DAG was successfully executed, generating output SQL files and updating the Qtrat config JSON file. The legacy SQLs were modified and appended accordingly.

Handling of Rule Descriptions and Templates

• Standardizing rule descriptions  
  Sachin suggested converting existing rules into a standard rule description format. Although there are around 100-200 rules (excluding threshold checks), some rules are complex and may not fit the standard format.

• Challenges with custom and complex checks  
  For rules that do not fit the standard format, a free-text description approach may be used in the update requests. The UI will display the role description, but some complex checks may require special handling.

• Template segregation and pattern matching  
  The system uses pattern matching via regular expressions in Python code to assign templates based on keywords in the rule descriptions. For example, missing value checks are filtered and matched to one of 13 templates.

• Handling percentage values and parameters  
  Percentage values and other parameters are extracted from the description using hardcoded positions in the code to generate the appropriate queries.

• Need for uniform descriptions  
  Uniform rule descriptions are critical for accurate template assignment and query generation. New rules will follow the standard format via forms, but legacy rules require analysis to determine fit.

Testing and Validation Plan

• Analysis and segregation of rules  
  Ayyappa will analyze the rules to identify which fit the standard templates and which do not. Based on this, decisions will be made on how to handle exceptions.

• Running all templates for missing value checks  
  All 13 templates for missing value checks will be run and results shared with Rachna and Anand for validation. The goal is to reduce the number of templates if possible.

• Focus on key check types  
  The immediate focus is on valid value, missing value, and duplicate checks, excluding threshold checks for now.

• Testing of duplicate check changes  
  Although duplicate checks were aligned previously, they still require thorough testing due to recent changes.

• Scheduling UAT and demo  
  UAT is tentatively planned for Friday after code adjustments by Prithvi. The next two days’ demos will be canceled to allow preparation.
