📒Meeting Outline

Data Quality Task Management and Email Escalation

• Issue with Open Testing Tasks  
  The team discussed the presence of multiple open tasks in the lower environment created for testing purposes. These tasks were not closed earlier, causing unnecessary escalations and email notifications. It was agreed that these duplicate and test records would be closed promptly to avoid confusion.

• Email Notification Configuration  
  The current setup sends emails from the normal environment, which is not ideal. A new build is being developed to ensure that emails related to testing tasks do not go to the main email ID, preventing unnecessary escalations. Kundan is assigned to handle co-deployment for this fix.

• Credential and Access Issues  
  There was a brief discussion about credentials (A2) required to close tasks, confirming that the same credentials apply for task closure.

Rule Modification and Approval Workflow Enhancements

• Mapping and UI Changes  
  Changes were made to the Actions page and Approve widget page to correct field mappings and improve rule description handling. The front-end will be updated based on the finalized template shared by Sachin.

• Standardizing Rule Descriptions  
  The team discussed the challenge of standardizing Data Quality (DQ) rule descriptions, as existing descriptions are varied and free-text based. Moving forward, a standardized template will be used for new rules, but existing ones will be maintained as is. Rachna emphasized considering the current Decoder project tree definitions to avoid issues.

• Disabling Fields During Rule Modification  
  Three fields—table name, variable, and check type—have been disabled for editing when modifying a rule to maintain data integrity.

• Approval Page Tabs for New and Updated Rules  
  Two separate tabs were added to the approval page: one for new rule requests and another for rule update requests. This separation aligns with different BPMN workflows and improves clarity.

• Tracking Changes in Rule Updates  
  Currently, only the latest data is shown without historical comparison. The team discussed the need to track and display previous and updated values for better change assessment. This would require backend changes and is planned for the backlog.

UI Enhancements and User Guidance

• Info Icons for Form Fields  
  To assist business users unfamiliar with QTRAG terminology, the team proposed adding info icons with hover descriptions for each input field on the UI form. Rachna will create a backlog item for this enhancement, and content descriptions will be provided for implementation.

• Handling Change Requests and Communication  
  Anand shared a list of change requests via email, which will be continuously updated. The team agreed to add new requests to this list and enhance the product iteratively after the initial launch.

SQL Generation and Data Quality Rule Execution

• SQL Query Generation and Legacy Updates  
  The process for generating SQL queries for DQ rules was demonstrated. The system updates legacy SQL files and the QTRAK config JSON with new DQ IDs. Multiple SQL files are generated per rule, and duplicates are avoided by appending entries.

• Testing and Promotion to Production  
  Currently, SQL generation is done without executing or storing results in test tables. The team discussed the need for a process to promote changes from development to production environments safely, considering environment restrictions on data writing.

• Variable and Description Usage in Rules  
  The system uses variable names and filter criteria primarily, with descriptions used to identify templates and capture specific inputs like percentage thresholds. Sachin requested a list of standardized descriptions and templates used so far to align UI and backend configurations.

• Data Quality Repository Queries  
  A query was run on the DQ repository to fetch missing value checks and validate descriptions. It was noted that some entries lack proper input parameters, which will be addressed in future discussions.

Deployment and Testing Updates

• Deployment Status  
  Nirmal reported deployment failures initially but confirmed successful re-trigger and deployment. Testing is planned post-deployment.

• Process Triggering and Context Data  
  The team discussed the need for flexibility in passing context data to trigger processes and create tasks dynamically.
