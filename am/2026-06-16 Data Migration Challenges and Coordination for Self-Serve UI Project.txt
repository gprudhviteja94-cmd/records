📒Meeting Outline

Data Migration and Table Structure Issues

• JSON Object Field Change and Code Updates  
  Discussion began with a query about whether code changes were made to accommodate a field changed to JSON objects. AYAPA and others confirmed that the business justification field needs to be changed from string to JSON object in the database schema. Attempts to alter the data type directly in BigQuery were unsuccessful, so it was agreed to keep it as string for now and convert to JSON in the application layer.

• Data Migration Challenges and Incorrect Data  
  There was confusion about the source of data and incorrect data being migrated, including unexpected entries like "airline free credit" which do not belong to the current use cases. The team identified that some data was mixed up with Quantro data, which is unrelated to the self-serve UI project. It was clarified that the DQ artifacts table being used is actually for Quantro, not for the self-serve project, causing confusion and errors.

• Table Creation and Missing Tables  
  AYAPA admitted missing the creation of a required clone table of the DQ repository for the self-serve UI, which caused delays and confusion. It was confirmed that the DQ artifacts table is an old table for Quantro and not suitable for current migration needs.

• Data Consistency and Mapping  
  The team discussed the need for data consistency between the IS database and the LUMI system, emphasizing that only about 230 "OK" records should be migrated, excluding threshold checks and complex records. The importance of mapping fields correctly and ensuring the data format matches the target schema was highlighted.

• Automation and Queries for Migration  
  AYAPA shared the insert and update queries used for migrating data, with some fields removed due to absence in the target table. Prithvi and others discussed the need for a streamlined approach to avoid manual updates and to automate the migration process as much as possible.

Use Case and Data Validation

• Use Case Identification and Validation  
  The team ran queries to identify distinct use case names and validate the data against production environment records. They confirmed the presence of 286 records excluding threshold checks, with 230 marked as OK and 56 as complex or duplicates to be handled separately.

• Data Format and API Calls  
  Issues with UI calling unnecessary APIs on modify actions were discussed. It was clarified that no API calls should be made for certain UI operations, and this was a UI issue to be fixed by the UI developer (Author).

• Data Format in SFTP and JSON Usage  
  The data transfer via SFTP was discussed, emphasizing that the file should be in JSON format rather than CSV or pipe-delimited to avoid parsing issues. The team agreed to use JSON files for data transfer and processing.

Coordination and Next Steps

• Responsibility and Deadlines  
  Sachin emphasized the urgency to complete the migration by 4:00 PM the same day to allow verification and subsequent steps with the DBA team for production migration. AYAPA committed to completing the migration of the 230 records by this deadline.

• Future Meetings and Follow-ups  
  A follow-up call was scheduled at 5:00 PM to review progress and address any remaining issues. Sachin stressed the importance of professionalism and timely completion to avoid further delays.

• General Observations and Process Improvements  
  Sachin highlighted the confusion caused by mixing tables and data from different projects (Quantro vs self-serve UI) and the need for clear documentation and access control to avoid such issues. The team agreed to improve coordination and data validation processes.
