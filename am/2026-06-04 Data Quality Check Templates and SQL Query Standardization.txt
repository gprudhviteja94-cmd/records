📒Meeting Outline

Data Quality Check Templates and SQL Query Formation

• Challenges with Descriptions and SQL Queries  
  The team discussed how the current descriptions for data quality checks (e.g., 100% fill rate, null values greater than 1%, duplicate checks) directly influence the formation of SQL queries. However, the descriptions vary widely, making it difficult to create uniform SQL templates that can handle all cases. For example, different descriptions for duplicate checks require different SQL queries, which complicates template standardization.

• Existing vs. New Rule Handling  
  It was clarified that past rules have diverse descriptions and SQL queries, requiring multiple templates. Going forward, new rules will follow a standardized input form, resulting in a single template per check type. This standardization will simplify SQL generation for new entries, but legacy rules will need special handling.

• UI Form Template vs. Free Text for Complex Checks  
  The team agreed that rules fitting the standard template will be editable via segmented UI forms, while complex or non-conforming rules will be shown as free text for manual editing. A "complex flag" will be used to identify such rules, enabling the UI to toggle between form-based and free-text editing modes.

• Segregation and Mapping of Existing Templates  
  Prithvi was tasked with analyzing existing rules to identify which templates align with the new UI form and which should be marked as complex. Examples like missing value checks and stagnant data checks were discussed to illustrate how some descriptions can fit the template while others cannot.

• Handling Updates and Edits  
  It was emphasized that for existing rules fitting the UI template, users will edit only the segmented fields, not the free-text description. For complex rules, free-text editing will be allowed. The backend will need to support these distinctions to ensure proper SQL query generation.

• Future Enhancements and AI Integration  
  Complex checks that cannot be handled by current templates may be enhanced in future iterations, potentially leveraging AI to automate or simplify SQL generation for such cases.

Collaboration and Next Steps

• Coordination with Ayyappa and Product Team  
  Prithvi was advised to work closely with Ayyappa, who has a strong understanding of the existing templates and updates, to identify overlaps and ensure proper mapping to the new UI templates.

• Clarifications on Rule Identification  
  The team confirmed that there is an identifier to distinguish new rule creation from rule modification, which will help in managing updates appropriately.

• Avoiding Excessive Free Text Usage  
  The importance of minimizing free-text descriptions was highlighted to prevent users from making unsupported edits that could break backend SQL generation.

• Acknowledgement of Migration Complexity  
  It was acknowledged that migrating existing rules to the new system is complex and requires careful analysis and phased implementation.

📋Overview

• Prithvi will analyze existing rules to map them to new UI templates or mark them as complex.  
• Users will edit segmented UI fields for template-fitting rules and free text only for complex rules.  
• Collaboration with Ayyappa is critical for understanding and mapping existing templates.  
• Future enhancements may include AI to handle complex checks more effectively.  
• Migration of legacy rules is recognized as a non-trivial task requiring careful handling.
