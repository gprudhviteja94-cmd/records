📒Meeting Outline


Automation job / DQ repository -> SQL generation

  • Current implementation & demo The automation reads new entries from the DQ repository table (for demo, a CSV is being used). For each entry it generates SQL files based on check type (duplicate, stagnant, etc.). The script is currently run locally; DAG implementation is in progress and expected to be closed today. The CSV includes rule description, check type, table/column details, and may include an added status column to mark processed rules for testing.

  • SQL file generation logic For each rule entry the script:
    
    • selects the appropriate template (based on check type)
    • generates SQL and creates folder(s) per check type (duplicate/stagnant currently)
    • determines schedule (daily/monthly) from the input and finds matching existing SQL files
    • if an existing SQL file is found for the table+schedule, it copies and appends the new SQL at the end (so multiple requests for same table are appended into one file)
    • if no legacy SQL found, it creates a new .sql file that contains only the SELECT statement from the template (minimal creation)
    • for demo, duplicate check uses one template; stagnant checks use three templates; most rules fit those templates.

  • Behavior for multiple checks on same table The automation currently preserves check-type folder segregation. If a table has both stagnant and duplicate checks, separate SQLs may be created under separate check-type folders, resulting in duplicates of the table-level file. The tool appends to whichever file it finds in the target folder for that check type.

  • Observed limitations & current practical behavior
    
    • Folder segregation by check type can produce duplicate files for the same table across different check-type folders.
    • The automation does not currently prevent parallel processing/merge conflicts if multiple checks for the same table are processed concurrently.
    • If no existing SQL template/file is found in the legacy folder, the script only creates a simple SELECT-based SQL (no merge).

  • Reporting / visualization A simple HTML report/view was created to review generated SQL and compare with legacy SQL. A summary report (records received, success count, description, files created) can be produced and emailed to stakeholders after execution—this is planned to be added.

  • Next checks to implement Future sprints will add support for threshold checks, valid value checks, and further duplicate-check coverage.


Design decisions / consolidation discussion

  • Segregation vs single repository Sachin, Arun and others discussed pros/cons of keeping generated SQLs segregated by check type vs a common repository:
    
    • Segregation makes maintenance and debugging easier for each check type.
    • A single common repository would avoid duplicate files for the same table, but requires additional logic to detect and merge files, ensure idempotency, and handle concurrent updates.
    • Refactoring is required if the team decides to change current structure (existing merged files exist in production). A POC is needed before making structural changes.

  • Merge / concurrency concerns Concerns raised:
    
    • If multiple checks for the same table are processed in parallel, race conditions and conflicting file updates may occur.
    • The automation needs a check to avoid re-downloading or re-creating a file if it already exists in the target location, and a merge strategy when appending new checks for the same table from different check types.
    • Team agreed to analyze complexity and make a decision in 1–2 days.
