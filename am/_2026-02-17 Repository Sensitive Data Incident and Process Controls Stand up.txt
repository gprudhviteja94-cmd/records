📒Meeting Outline


Repository sensitive-data incident & process controls

  • Incident description and origin The team discussed a CSV file containing credit card numbers and other sensitive data that had been committed to the repository. The file had been deleted previously (around five months ago) but resurfaced in the develop branch. Participants reviewed history and commits to identify the origin; one hypothesis was that deletion occurred in a fork and not in the main branch. A renamed branch that was not deleted was identified as part of the cause. Ayapa was mentioned as possibly involved in changes that led to the file reappearing.

  • Risk and organizational impact Tools (scanners) flagged the repository with many credit cards and passwords linked to the environment; the report shows 42 credit cards and passwords associated with the team. Leadership visibility and perception were a concern — the incidence is considered high risk because the organization is financial and handles PII/PCI-sensitive data. Team leads expressed that repeated occurrences create a poor impression and could be escalated by leadership.

  • Expectations & rules Strong instructions were reiterated: do not commit PII or any sensitive information (credit cards, passwords, HD fields) to any repository branch (dev/feature/main). Developers must be cautious about local activities and commits. Team members were reminded of previous guidance (e.g., not using PII with LLMs). It was noted some members are new and may not fully understand the risks.

  • Immediate mitigation & scan behavior The scanning tool’s refresh/scan results were questioned — post-deletion scans did not appear to reflect removal immediately. It was mentioned that secrets were still visible and branch renaming/retention complicated cleanup. A plan to investigate commit-by-commit was discussed to find the originating commit. Team ownership and buy-in for cleanup were highlighted; one suggestion was asking developers to clean up their own forks/branches.

  • Process change: mandatory review A lead (appeared to be Sachin) decided that no code commits to the developer branch will be allowed without their review going forward. They will enforce reviews even if it delays merges up to two days. This is to prevent future PII/secret commits into the dev branch.

Data access, environment guidance, and UI feature changes

  • Data access policy & requests For data queries the team should request only Data Reader access (not HD) on individual IDs for environments E1 and E2 (avoid E3). PII fields will be encrypted for Data Reader roles; if additional validation is needed, product partners can run queries. The team should not request HD/sensitive access.

  • UI: distribution list, use case registration and workflow Current UI includes distribution list, use case list and “Register your use case.” Discussion covered replacing free-text “register your use case” with dropdowns:
    
    • Proposed behavior: distribution list dropdown → auto-populate use case dropdown based on selection; then user submits.
    • If a user’s distribution list/use case is not available, a non-mandatory text box for “register your use case” can be provided (with justification/notes). On submission, if text box has value, backend should call API to register the use case; if it's empty and other values present, initiate the watcher.
    • Backend complexity concern: auto-registering entries into use case table without an approval workflow may lead to issues (no approval flag exists currently) and makes deletion/cleanup harder. The lead will consult Anand and Rachna before implementing auto-registration.
    • Interim approach: park the auto-registration change, add a justification/notes field for approval/rejection workflow, and share use case table/column details with the UI owner to proceed on safe changes.

  • Next steps for UI implementation The UI should:
    
    • Remove the redundant “register your distribution list” field.
    • Make use case selection auto-populated from distribution list where applicable.
    • Provide an optional text box for ad-hoc use case registration only when necessary (non-mandatory).
    • Backend and product team alignment required before enabling auto-registration.
