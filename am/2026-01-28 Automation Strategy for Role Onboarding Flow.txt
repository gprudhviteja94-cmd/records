📒Meeting Outline


Role onboarding & overall flow

  • Overview of requirement The team is building a self-serve role-onboarding flow where customers submit inputs via UI to create DQ (data quality) rules. After approval, data flows from the ACE database to the Lumi warehouse. The next initiative is to build an automation utility (batch job) to process these inputs and integrate new/changed rules into existing Lumi processes.
  • End-to-end data movement Initial landing: partners push files to SFTP → files are ingested into ACE DB → data pulled to Lumi workspace. The utility will read files from SFTP and insert file details into a DQ repository (projectly ext table) in the Lumi use-case folder (not the warehouse).


Automation utility responsibilities and design

  • Job steps (high level)
    
    1. Read file(s) from SFTP.
    
    2. Insert file metadata/details into the projectly ext table in Lumi workspace.
    
    3. Run an automation job daily to:
       
       • Read the latest available data (but pick up only previous-day data for processing).
       • Identify rule properties: role type (daily/weekly/monthly/intraday) and check type (threshold/stagnant/missing/duplicate/valid etc.).
       • Create or modify tags (do not create duplicate tags; modify existing tag files like daily/monthly/weekly tags for the table).
       • Create or modify the SQL script file(s) for the rule (or DAG configuration) and place the resulting files in a specified location for developer commit. Attempted Git commit automation is being investigated (auth/token required) but may not be feasible; if not possible, files should be staged for manual commit.

  • Tag & DAG handling Existing DAGs/tags (e.g., C360_daily tag) should be updated to include newly added rules where applicable. The process should add the rule to the correct tag (daily/monthly/etc.) rather than generating a new tag. If the existing DAG requires framework code changes, preference is to modify configuration rather than Python files. If modification of Python is unavoidable, consider Git commit feasibility; otherwise place files for manual developer commit.

  • SQL file handling & pattern Observations: many existing SQL files exist for one table (e.g., CM11), often with a large shared common pattern (select ... union distinct ...). The desired approach:
    
    • Make the common portion constant/template and dynamically append DQ-specific queries (union distinct blocks) so one consolidated SQL per table can be maintained rather than many files.
    • When UI creates a new rule, the automation should append the new rule’s query block to the unified file (or generate a SQL file following the single-file-per-table rule).
    • If immediate full refactor is not possible, allow a transitional approach: new tags for rules can be created but moving forward single SQL per table is required.


Analysis & distribution of work on check types

  • Action for team members The team must analyze existing SQL scripts and classify them by check type (threshold, missing value, duplicate, valid-value, stagnant). Identify patterns and commonalities in the SQL structure:
    
    • Each person should review multiple SQLs (not just one). Recommended: 3–4 SQL files per assigned check type to ensure robust pattern identification.
    • Distribute check types among the team: those with more bandwidth take two check types; others take one.
    • Deliverable: a confirmation/report of findings by tomorrow morning (DSU) to guide design decisions for automation and SQL consolidation.

  • Scope for Prithvi Prithvi (new to project) should be given consolidated inputs from the team to help build the utility. Team should provide sufficient scripts and patterns to accelerate his ramp-up. From next week he must increase delivery velocity.


Technologies, scheduling & infra

  • Airflow & language Apache Airflow will be used for scheduling (DAGs). Python is the primary language for the DAGs and automation code. Shell scripting can be considered for small tasks but Airflow + Python is the primary recommendation.

  • Deployment / Lumi platform Automation will run on Lumi platform. The first steps (SFTP -> ACE DB) are already in place; we need reverse read capability from ACE DB/SFTP to Lumi. The utility will operate in Lumi, stage generated SQL/DAG files into a repository area. Git commit automation with token/ADS ID is under investigation; if not feasible, files will be staged for manual commit by developers.

  • Phasing
    
    • Phase 1 (immediate): SFTP file-read and insert into Lumi DQ repo; daily automation job to pick previous-day data and identify rule metadata. Start next sprint (from Tuesday).
    • Phase 2: Generate/modify SQL files and tags; attempt Git automation; if not possible, provide files for manual commit.
    • Phase 3: Consolidate SQLs into single-file-per-table design and refactor DAGs/config as needed.


Risks / constraints / clarifications

  • Many existing SQL files per table (e.g., CM11) cause maintainability problems — must consolidate.
  • Git commit automation requires authentication tokens and may not be feasible; manual intervention fallback must be supported.
  • Changes to Python framework may be undesirable; prefer config-based changes where possible.
  • Steps and design are not fully final — may change with further discovery. However, the first 2–3 core steps (SFTP read, DB insert, automation pick & create/modify artifacts) will remain.
