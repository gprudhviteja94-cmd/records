Business Logic & Alerting Rules

  • Primary flow for alerts For each monitored table:
    
    1. Check if there is ingestion entry for today's date. If none, consider failure alert.
    2. If entry exists, check latest "staging to main copy" task status for that table — if failed, get the error summary from audit logs and include in the alert.
    3. Email alerts are sent only on failure. If N tables fail, N emails should be triggered (one per table), not a single email for all.
    4. The value/error details for the alert should be derived from audit logs (match by table name and task ID).

  • Scope Initially implement for one table (insurance table / TV06x example), validate end-to-end, then extend to all ~10 insurance-related tables. Once stable, scale to more tables.

  • Queries There are at least two queries expected: the ingestion check and the additional audit-log status/error query. Owner to provide missing query text (Sachin/Kundan to share).


DQ Templates & Automation (Self-serve automation)

  • Template approach overview The group reviewed DQ repository rules and identified that most checks can be mapped to a small set of templates. Proposed mapping keys: check type + description (+ filter criteria when needed). The description will be standardized from the DQ repository content; users should not freely author arbitrary descriptions — automation will use the standardized descriptions.

  • Stagnant data check Analysis shows stagnant checks likely fit into 1–3 templates. The team observed about 70 stagnant rules (out of ~1588 DQIDs) — manageable. Approach: map existing stagnant rules to templates (daily/monthly/weekly variations may require separate templates). If some queries do not fit a template, modify queries (while ensuring final results match current DB outputs).

  • Valid value / Expected value / Missing / Duplicate checks
    
    • Valid value checks appear to share common patterns; templates can be created where filter clauses are parameterized.
    • Expected value may become a user-supplied input parameter going forward — product team to confirm.
    • Missing value checks and duplicate checks: duplicate checks are relatively few (e.g., 9) and can be closed quickly; missing value counts around 110 — require template mapping.
    • For checks whose SQL changes by frequency (daily/monthly/weekly), create separate templates per frequency group.

  • Template key components To minimize template count, template selection should consider:
    
    • check_type (stagnant, valid_value, missing, duplicate, threshold, etc.)
    • rule_description (standardized human-readable description)
    • filter criteria (if present and impacts SQL structure) Combined these produce a deterministic template selection for SQL generation. Dynamic parts (filters, columns, constants) will be parameterized into template placeholders.

  • Next steps for templates
    
    • Analyze all stagnant rules (70) and classify patterns to determine final template count.
    • Perform similar classification for valid value, missing, duplicate checks.
    • Aim to finalize at least one stagnant template and POC by tomorrow (target: lunch).
