📒Meeting Outline


ACE Reporting & Onboarding Process

  • ACE reporting high-level fit The session opened by placing ACE reporting within the ACE ecosystem. When a tenant needs a use case on ACE, requirements are gathered, a tenancy is created (ILM tool used to automate ILM tenancy requests), BPMN is developed and deployed to AS tenancies. ACE reporting captures events from Kafka topics and injects them to Elasticsearch/Kibana for visualization (tables, charts, graphs).

  • Reporting applications and onboarding artifacts The reporting platform requires tenants to provide three reporting-side applications/configurations: PI registry, PI event ingest, and PI egress. PI registry requires a registry.json in a specified format (includes PI deployment ID — a UUID that uniquely identifies a use case). The registry defines index name, ES index name, application ID (car ID), application name, source, and deployment IDs to capture. A flag viewEnabled (true/false) controls whether child indexes are created.

  • Indexing and ingestion flow Events produced by BPMN/use cases go to Kafka topics. Ingest applications read from topic names and use configured transformers to convert payloads to JSON suitable for Elasticsearch. The ingest application plus transformers and mapping.js entries determine how fields/properties appear in Elasticsearch indexes.


Elasticsearch / Kibana Index Management

  • Index templates and settings Before creating an index, an index template is created that defines index name patterns, index settings and aliases. Templates include alias names (used instead of direct index names), shard count, number of replicas, and other index-level configurations. Aliases can have roles/rules and help route writes/reads without changing actual index names.

  • Shards, replicas and storage considerations Shard count and replicas are configured in the template. Shard size guidance (e.g., ~30GB per shard) and min/max docs per primary shard are part of index settings. These determine how data gets distributed across the cluster and influence performance/storage.

  • Index lifecycle management (ILM) policies ILM policies are used to manage data lifecycle across phases: hot (active), warm (less active but occasionally queried), cold (infrequently queried), and delete (retention). Rollover can be enabled with thresholds by size or age. Retention policies differ by environment:
    
    • Default/typical retention currently 180 days (was 700 days historically)
    • Some environments (E1) may have 15 days
    • Some indices (exceptions) have 30 days (example: roles index) Tenants cannot change retention directly; they should request changes from the platform team.

  • Dev Tools / Queries for index operations Kibana Dev Tools are used to run queries for index creation, data fetch, deletion, reindexing (move data from one index to another), and other manipulations. Examples discussed:
    
    • Delete by query for a deployment ID within a time range.
    • Reindex from a source index to a destination index with filters (e.g., by car ID / deployment ID). Resharding for E3 is handled by another team (XPAAS/desktop platform), not by the XPAAS reporting team.


Kibana Visualization & Dashboard Questions

  • Data availability vs. dashboard display If properties/fields are present in Elasticsearch (visible in Discover) but not shown on dashboards, the tenant must ensure those fields are included as properties in the registry payload (registry.json) and mapping. Dashboard creation/modification is generally tenant responsibility; the platform ensures ingestion and availability in Kibana.

  • Dashboard creation support limitations The platform team guarantees data ingestion and availability in Elasticsearch/Kibana but does not provide extensive dashboard-building support for each tenant. Tenants can create tables, charts, and dashboards in Kibana, selecting properties that exist in the index mapping. The team offered to check specific cases offline and provide documentation links; tenants may also reach out to Gaurav for further help.


Child / Parent Index Structure (viewEnabled example)

  • Parent and child index relationship When viewEnabled is true, a parent index holds multiple deployment IDs and child indexes are created per deployment ID. Child index definitions include index name, app details (car ID, application name), shard/replica settings, Kafka topic name, and transformer name for ingestion. Mapping.js and transformer configuration must be updated to capture correct fields.

📋Overview

  • ACE reporting ingests Kafka events into Elasticsearch/Kibana for tenant dashboards.
  • Tenants must provide registry.json (PI registry) with deployment IDs, index names, and properties so fields appear in ES indexes.
  • Index templates define patterns, aliases, shards, replicas, and settings before index creation.
  • ILM policies manage hot/warm/cold/delete phases; retention defaults to 180 days with exceptions (e.g., 30 days for some indices).
  • Kibana Dev Tools support index creation, deletion, reindexing, and other management queries; resharding may be handled by a different team.
  • Dashboard building is tenant-responsibility; platform ensures ingestion and field availability but limited dashboard support is provided.
  • Child indexes are created when viewEnabled=true; transformers and mapping.js updates are required for correct field capture.
  • Remaining details to be covered in next session; contact Gaurav or platform owner for more information.
