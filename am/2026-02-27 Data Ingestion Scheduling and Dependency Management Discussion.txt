Data ingestion scheduling & Maestro dependency

  • Weekly job behavior The team discussed that the weekly tag/job will pick up whatever latest data exists in the target table at run time (e.g., weekly aggregation covering the previous week). If the business only needs the latest available data/materialized weekly, there is no need to create a Maestro dependency link. The key is clarifying whether the job must run only when a new/latest record appears or always run on schedule regardless of new data.

  • When Maestro dependency is required If the requirement is to run only when new/latest ingestion exists (i.e., discard runs with no new records), then a Maestro dependency (or equivalent) is required to check for latest records before executing downstream processing. If the requirement is to always process whatever data exists in the table on the scheduled weekly run and produce the report, Maestro dependency is unnecessary.

  • Clarify business requirement Actionable point: confirm with business partners whether the pipeline must:
    
    • run only when new/latest data is present (requires dependency/guard), or
    • run on the schedule regardless and generate a report from existing table contents (no dependency). Also confirm exact schedule semantics (e.g., weekly on Friday) and what time window the SQL aggregation should cover (example: last Friday-to-Thursday).


Query logic and failure notifications

  • Query time window and filtering The team reviewed SQL query criteria: an example was filtering records with date >= 2024-01-01. Need to ensure the query’s WHERE clause matches the intended aggregation window (weekly, hourly, last one hour for failures, etc.).

  • Failure detection frequency For failure monitoring, there was confusion about frequency: one person modified CD load to run hourly and this caused repeated email notifications. The intended behavior is:
    
    • If failure detection is to check last one hour (for an hourly job), send notification only if failures exist in that last hour.
    • If detection runs on a scheduled daily/weekly basis, use the corresponding time window. The change to hourly without finalizing requirements led to noisy alerts; the team agreed to confirm required cadence before merging such changes.

  • Email notifications logic The query used to find failed records pulled for the current date; this caused missed or repeated alerts (e.g., if job fails yesterday, a query for today shows no failure). Need to align date logic with the intended failure window to avoid false negatives/positives.
