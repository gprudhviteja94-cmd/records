📒Meeting Outline

Template selection & automation approach for DQ SQL generation

• Common templates and patterns
  The team reviewed existing DQ SQLs for RAC-related tables (RACI user reservation, user venue, RACI user) and identified recurring query patterns. Duplicate-check queries follow a consistent template (Template A). Other checks (null/valid value/field-key checks) follow other reusable patterns. There is agreement that many existing SQLs can be categorized into a finite set of templates (example: 20 templates) and new DQ rules should map to one of those templates with parameter substitution (table name, columns, conditions).

• How to pick the right template
  The group discussed that selecting the correct template for a new DQ rule requires an input parameter indicating the check type (e.g., duplicate, null, valid-value). Duplicate-check -> Template A is straightforward. For Template B/C/D (null/valid value/other), team members requested clarity on exact criteria (which input flags or metadata indicate which template to use). There is no final, agreed automated decision rule yet — business input is required to map rule types to templates.

• Edge cases and per-table differences
  Even when templates are shared across tables, small variations exist (e.g., feed_key filter present in reservation table queries but absent in venue table). These differences mean templates must support optional parts or provide table-specific parameters. The team recognized potential conflicts where multiple templates might apply to the same table; thus, deterministic selection criteria are needed.

• Automation vs manual integration
  Two approaches discussed:
  1. Full automation: The automation picks up DQ rule input, generates SQL using templates and merges/updates existing SQL in repository automatically. This requires reliable identification of template for each incoming rule (which currently lacks a robust, consistent input).
  2. Hybrid (alternate) approach: Automation ingests rule input, generates a new standalone SQL file and stores it in a staging area. A developer then manually inspects and integrates the generated SQL into existing sequences/files and commits to Git (manual merge/integration step). This reduces automation complexity (automation produces SQL but does not alter existing SQLs), at cost of some manual work.
  Team leaned toward the hybrid approach if template selection inputs are not provided by business.

• Tooling concerns (VS Code plugin / LLM)
  Usage of a VS Code plugin or developer-local LLM/Copilot was debated. Concerns:
  • Management overhead of installing and updating plugins on multiple developer machines.
  • If plugin or LLM logic changes, updates must be propagated to all developers.
  • Uncertainty if plugin/LLM will run in the target environment.
  Agreement: If plugin/LLM can be run centrally in environment, it could be acceptable; otherwise avoid reliance on per-developer local installations. The hybrid automation is appealing because it minimizes local setup needs.

• Need for business input
  Repeated point: To fully automate template selection, product/business partners must provide metadata or selection guidance when onboarding new DQ rules (e.g., rule type = duplicate/null/valid-value or explicit template ID). Without such input, automation cannot deterministically select templates.

SQL quality, reuse and optimization

• Common utility framework and SQL improvements
  The existing data-quality execution and monitoring framework was acknowledged as substantial work and operational in production. Team has earlier refactoring efforts: moving common expressions/libraries to top of scripts and referencing them to reduce duplication. Some scripts have adopted these improvements; some still need refactoring. Samir (SQL expert) provided optimizations and expressions that have been adopted in part; further optimization may be possible but limited by business constraints.

• Handling Many Patterns
  Concern that thousands of patterns/rules exist and without identification input automation will struggle. The suggestion is to either require pattern selection input at rule creation time or adopt the hybrid workflow to reduce automation scope.

Specific alert / rule validation discussion (insurance policy counts)

• Observed alert anomaly
  Ansi presented an alert for insurance-related DQ rule comparing unique policy counts "today" vs "yesterday". The rule expects today's unique count >= yesterday's unique count, but team noted this assumption can be invalid because daily ingestion volumes vary and unique counts can decrease day-over-day (e.g., if fewer records are ingested). The rule may therefore be overly strict or incorrectly configured for daily comparison.

• Clarifications and follow-up
  Rachna had earlier noted some failures were expected due to latest ingestions for one of the rules. The team agreed to check expected business logic with Rachna and the data owners to confirm whether the comparison semantics (daily vs aggregated/rolling window) are correct and whether the rule should be adjusted (e.g., compare weekly or use different threshold logic).

• The existing DQ SQLs exhibit repeatable templates/patterns (duplicate check, null check, valid-value check, feed_key differences).
• Duplicate check mapping to Template A is clear; mapping rules for other templates remain unclear and require input.

• VS Code plugin / LLM usage has operational concerns (installation, updates, environment compatibility); centralized runtime would alleviate issues.
• Refactoring/optimization of SQLs (common utilities moved to top) has been partially applied; more scripts need alignment.
• Insurance policy count rule appears to be wrongly assuming monotonic non-decrease of daily unique counts; business clarification needed.
