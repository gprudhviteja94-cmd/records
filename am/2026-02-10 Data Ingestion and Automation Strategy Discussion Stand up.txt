Automation / self-serve generation of SQL rules and templates

• Overview of current investigation
  Discussion: Team reviewed several tables (CM11 CSP model, CM11 iPod edit, Raze tables) and observed multiple SQL patterns for the same check-types across tables. Columns (A, B, C, D, E, F) were used to illustrate different SQL templates/patterns. When a user registers a new rule, the system must choose which template to apply or generate a new SQL. The problem: selecting which template to use when existing templates vary considerably even within a single check type.

• When to apply where clauses / filter conditions
  Discussion: If user input contains filter conditions, include WHERE clause; if not, do not add WHERE. Variation arises from different patterns like full-refresh (stagnant) versus incremental (load-up) tables. For full-refresh tables, previous day's data may not be present in source; DQ results or inner joins to previous snapshots are sometimes used. For load-up tables, date filters can be applied directly. Team discussed rules for differentiating templates by these characteristics.

• Template divergence causes and possible consolidation
  Discussion: Divergence is often caused by differences in:
    • Whether table is full-refresh (stagnant) vs incremental (load-up)
    • Use of inner join with SOR vs joining with DQ results
    • Presence/absence of user-provided filter criteria
    • Different calculation style across check types
  Team agreed some divergent cases can be normalized by consistently using DQ results (store today's DQ results, then use them for comparisons), enabling reuse of a single template across more cases. But not all cases can be forced into one template.

• Approach for new/complex rules
  Discussion: Proposed flow:
    • Receive user description and inputs
    • Generate a SQL query (or SQL file) automatically from the input according to identified patterns
    • Attempt to match the generated SQL to an existing template (and update existing SQL/JSON with new rule ID if it fits)
    • If it does not fit, produce a generated SQL artifact which developers will review for feasibility (possible commit to repo or replacement of the existing SQL)
    • For complex cases that cannot be auto-fit, keep a manual developer step to integrate/generate final SQL
  Team emphasized they must avoid creating new tags for every new rule (would bloat scheduling and management). Instead, reuse tags (daily, intraday, monthly, ELA) and attach new rules to existing tags where appropriate.

• Automation vs manual intervention
  Discussion: Currently at an early stage; initial POC will target simpler, matching patterns to automate generation and integration. Complex cases will require manual dev review. Over time, if the team can reliably accommodate generated SQL to existing templates, more automation can be introduced. Team agreed to proceed with POC for simpler matches and reconvene to refine approach for complex cases.
