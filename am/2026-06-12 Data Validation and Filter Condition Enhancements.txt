Data Validation and Filter Condition Handling

• Review of Data Columns and Expected Values  
  The team reviewed the data provided in column F and cross-checked it with the email sent to Athar and Sachin. There was initial confusion about column names and data updates, but it was confirmed that the current data is fine after filtering out stagnant data checks.

• Handling of String Values in Filter Conditions  
  It was discussed that string values used in filter conditions should be enclosed in quotes to avoid backend failures. The approach will depend on the column data type: strings will be quoted, while numeric values may not require quotes. This feature is not yet implemented and will be added, with Sachin to be informed.

• Check Type Corrections and Description Updates  
  Several data quality checks were reviewed for correctness in their classification as "valid value" or "missing value" checks. For example, checks involving counts of records with values not positive or invalid date formats were corrected to valid value checks. Descriptions were updated to align with the latest UI format, including consistent use of zero percent thresholds for null values.

• Filter Condition Enhancements  
  New filter conditions were added or corrected, such as ensuring customer ID is not null when a customer indicator equals one. The team agreed to update descriptions and filter conditions accordingly.

• Handling Complex Checks and Template Development  
  Complex records and checks were discussed, with some being moved into simpler valid value checks by adjusting filter conditions. It was noted that queries generated from new templates will differ from old ones, so outputs will be generated and reviewed side-by-side to validate correctness. Sample queries for four check types will be prepared by Monday morning for review before template creation.

• Data Format and Delimiters in UI  
  The team agreed to use commas as delimiters in UI inputs instead of slashes to ensure correct parsing. Also, there was a discussion about whether the front end can enforce quoting of string values or if this should be handled in the backend. The preferred approach is backend handling based on metadata, but a fallback to manual quoting during request approval is possible.

• Duplicate and Obsolete Records  
  Duplicate records with the same DQID were identified and agreed to be deleted. Some records had been replaced but not updated in the environment, so cleanup was planned.

• User Guidance and Future Enhancements  
  It was emphasized that filter conditions must be provided in exact SQL format by users. This will be communicated during onboarding and noted in the UI. Although an agentic (AI-based) process to simplify this is planned for the future, current backend limitations prevent its immediate implementation. Poorna is engaging teams to obtain necessary permissions for AI integration.
