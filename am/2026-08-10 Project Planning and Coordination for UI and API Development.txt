Rule Creation and Modification Workflow

• The current focus is on completing changes related to rule creation, including rejection email updates, with additional work pending on rule modification.
• The entire offshore team is involved and must understand the criticality of the initiative.
• Detailed instructions were given on handling JSON objects for business code questions, including saving yes/no answers and associated ORE (Operational Risk Event) details in separate database fields.
• Specific data handling rules include:
  • For question 3, if "yes" is selected, ORE number and issue overview text fields become mandatory; if "no," these fields remain blank.
  • Boolean values should be used instead of strings for yes/no fields.
  • Complex SQL queries related to rules must be stored as text fields and executed safely.
• Validation logic should be implemented primarily on the front end to avoid unnecessary backend database calls, including case-insensitive comparisons and trimming inputs.
• Exception handling has been centralized to a single handler to avoid duplication.
• New use case registrations involve passing zero for "others" and no retry logic on failures to avoid duplicate data.
• Distribution lists for existing teams are fetched via database calls and used to populate alert fields.
• The process flow for rule creation includes immediate database entry, human task creation, email notification, and a daily batch process to update DQ artifacts with rule details.
• Approval or rejection of rules is managed via human tasks, with UI blocking approval actions until the rule status is ready.
• Auto-rejection occurs if no decision is made within 15 working days, triggering email notifications and status updates.

Automation and Data Quality (DQ) Artifacts Integration

• After rule creation, a scheduled batch process runs at midnight to update DQ artifacts with rule execution results.
• Complex checks require executing user-provided SQL queries in BigQuery, with validation to restrict queries to SELECT statements only, preventing insert or update queries.
• The business user inputs SQL queries for complex checks; access and syntax errors must be handled and reported accordingly.
• Execution results (actual value, expected value, pass/fail status) are saved back to DQ artifacts.
• A CSV file is generated nightly by ANSI, containing these results, which is then transferred via SFT to ACE for further processing.
• The automation DAGs are planned to be triggered sequentially or scheduled, with ongoing investigation into triggering DAGs from other DAGs to optimize scheduling.
• Email alerts for failures will be enhanced with capitalized "ALERT" tags in the subject line to help the tech team quickly identify and prioritize issues.
• Separate failure emails will be sent directly to the tech team without involving business users.
• The implementation phase involves creating human tasks for the tech team to deploy approved rules into the E3 environment, followed by email notifications confirming rule activation.
• Bulk implementation is supported, with tracking of who implemented each rule for accountability.

Reporting and Database Updates

• Reporting APIs will be created to extract active rule counts, variables tracked, and tables covered from the DQ repository.
• Queries will be grouped and optimized to provide counts rather than names for variables.
• Data migration scripts exist to preserve historical data during repository updates.
• Some database parameters and fields are pending updates from the DBA architect; the team is advised to proceed with implementation despite these pending changes.
• Coordination with the DBA is ongoing to finalize database schema changes to avoid repeated work.
