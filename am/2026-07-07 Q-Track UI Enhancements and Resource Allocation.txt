📒Meeting Outline

Q-Track UI and Self-Serve Enhancements

• Q-Track UI Creation and Backlog Status  
  Discussion started with the status of Q-Track UI creation. It was clarified that the Q-Track UI is not currently visible in the backlog, possibly because it has been released to production. New enhancements like creating a new page and access API are underway, mainly handled under the self-serve module (DQIM). Validation and implementation remain, with small testing and UAT planned before deployment to the E3 environment.  
• Story Creation and Sprint Planning  
  Multiple stories will be created: one for environment promotion, one for UAT, and one for E3 deployment, each estimated at one story point. Bulk update features require stories for SRE review and launch, also estimated at one story point each. Prioritization and assignment were discussed, with Anand and Cindy involved in deployment and review tasks. Some stories may be parked for the next sprint due to potential challenges.  
• Complex Rule Handling and Data Migration  
  Athar presented the handling of complex threshold check types, which require editable rule description fields as opposed to auto-formatted SQL for simple checks. A suggestion was made to add a complexity selector (simple/complex) in the rule creation UI to accommodate this. Existing rules were migrated accordingly, with further incorporation planned for the next sprint. Data discrepancies in a few records are being verified before final migration by the end of the week.

Rule Modifications, New Use Cases, and Resource Allocation

• Rule Modification Backlog and New Use Cases  
  It was confirmed that there are no pending rule modification items in the backlog, but a new use case involving approximately 300 checks is ongoing, with about half completed. The team discussed resource needs, with Anand requesting three resources to handle the workload, including EPA and CN.  
• Sprint Capacity and Story Assignments  
  Story points were allocated across team members for various tasks: 8 story points each for CD migration tasks assigned to Suman, Jeppa, and Ansi; 5 story points for KRI implementation to Kundan; 3 story points for multivariant POC to Vargav; and multiple story points for validation and API tasks to Sameer and Nirmal. Prioritization emphasized closing POCs and handling dependencies efficiently.  
• Cutover Planning for Threshold Checks  
  Discussion on the cutover plan to stop running threshold checks on Q-Track and start triggering email alerts from Control. The easiest approach suggested was inserting data directly into the DQ results table to maintain pipeline consistency. Design work will proceed in parallel with validation.

Data Migration, Pipeline Updates, and Discovery Initiatives

• Data Pipeline and Entity Discovery  
  Jason and others discussed the need to re-ingest pipelines with new IIQs and to prioritize data transfer initiatives from Lumi to Snowflake and MariaDB. It was agreed to create user stories for these tasks and plan calls to finalize requirements and priorities.  
• PI Sprint Planning and Discovery Completion  
  The team acknowledged limited sprints left in the PI and emphasized completing discovery tasks within this timeframe. Implementation work will follow in subsequent sprints. Coordination with the SFT team and infrastructure setup was highlighted as pending items.  
• Cornerstone Decommissioning Use Cases  
  Sravan raised the topic of cornerstone decommissioning use cases. It was clarified that most use cases are owned by Aman’s team and that the current team’s responsibilities are limited to Razy, which has been migrated. Further follow-up with Purna and others is planned to clarify ownership and next steps.
