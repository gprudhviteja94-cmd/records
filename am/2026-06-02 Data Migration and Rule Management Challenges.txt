📒Meeting Outline

Data Migration and Rule Management Challenges

• Migrating Existing Data and Rule Display on UI  
  The team discussed challenges in migrating approximately 300 existing data quality (DQ) rules into a new UI format. It was emphasized that relying solely on the auto-generated description field to represent rules is insufficient and can lead to missing validations. The consensus was to uniformly distribute rule conditions into structured filter criteria fields, similar to how inputs are captured in the UI forms, to maintain consistency and completeness.

• Handling Rule Modification and Display Consistency  
  While displaying existing rules on the UI is straightforward, modifying them poses challenges due to differences between old descriptions and new UI templates. A proposal was made to allow free-text input for modifications where structured templates do not fit, pending confirmation from the backend team (Arthur). The importance of maintaining a uniform backend format to support both display and modification was stressed to avoid managing multiple rule versions.

• Future Enhancements and Dynamic SQL Generation  
  The team considered future improvements such as using algorithms to dynamically identify modifiable fields and changes during rule updates. However, this is a longer-term goal, and immediate focus remains on finalizing the current migration approach.

Standardization of Filter Criteria and Description Fields

• Splitting Description into Filter Criteria and Additional Columns  
  It was agreed that the description field is only one component of the input data. Other columns (e.g., allowed null rate for missing value checks) must also be incorporated into the filter criteria. The team plans to extract as much information as possible from descriptions into structured fields, ensuring all necessary data for query generation is available.

• Avoiding PII Exposure and Using Automation Tools  
  To assist with data extraction and standardization, leveraging AI tools like GitHub Copilot and ChatGPT was proposed, with caution to exclude personally identifiable information (PII) such as email IDs and business owner names. Only non-PII fields like description and filter criteria should be processed through these tools.

• Adding Missing Filter Criteria from SQL Queries  
  Some filter criteria used in SQL queries are not currently captured in the DQ input data. These missing criteria need to be added to the input data to ensure accurate query generation and future-proofing.

Valid Value Check Template Simplification and Custom Checks

• Reducing Template Complexity for Valid Value Checks  
  The team agreed to limit valid value check templates to a simple array format where users input comma-separated valid values. More complex or infrequent valid value checks will be handled via custom checks with free-text input, avoiding the need to create numerous specialized templates.

• Handling Complex Checks and SQL Generation  
  For custom checks, a "complex" flag will be introduced on the approval page to bypass automatic SQL generation. This allows flexibility in handling complex or unique validation logic without overcomplicating the UI or backend.

• UI Enhancements Needed  
  Currently, the UI does not distinguish between custom and standard checks in the dropdown selection. Adding this distinction is necessary to implement the complex flag and improve user experience.

Project Planning and Next Steps

• Data Migration Timeline and Collaboration  
  The team aims to finalize the filter criteria distribution and description standardization by the next day to facilitate a review with Rachna and Anand. Collaboration with IFA and the database team is planned to support the migration, including preparing a Request for Change (RFC) with 48-hour advance notice.

• Ensuring No Impact on Existing Production Processes  
  It was highlighted that existing production SQL queries do not currently use filter criteria fields directly. However, a thorough check will be performed to ensure that modifications do not impact ongoing processes.

• Effort and Resource Allocation  
  Ayyappa and Prithvi will work on refining the solution details. The team acknowledged the effort required but emphasized the importance of completing this migration to avoid future complications.

• Migrating existing DQ rules requires distributing conditions into structured filter criteria rather than relying on auto-generated descriptions.  
• Displaying rules on UI is manageable; modification requires uniform backend formatting and possibly free-text inputs for unsupported cases.  
• Future dynamic SQL generation enhancements are planned but not immediate.  
• Description fields must be split into filter criteria and additional columns; missing criteria from SQL queries must be added.  
• Use AI tools cautiously for data extraction, excluding PII.  
• Valid value checks will use a simplified comma-separated template; complex cases handled via custom checks with a complex flag to bypass SQL generation.  
• UI improvements needed to distinguish custom checks and support the complex flag.  
• Data migration and standardization to be completed promptly with collaboration from IFA and database teams, ensuring no disruption to production.
