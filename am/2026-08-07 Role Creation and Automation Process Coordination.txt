📒Meeting Outline

Coordination and Role Creation Process

• Call and Attendance Confirmation  
  Sachin initiated the meeting, confirming all members were present and troubleshooting microphone and screen sharing issues. Emphasized the importance of everyone being on the call due to their involvement in different automation tasks.

• Role Creation Flow Overview  
  Explained the end-to-end flow of role creation integrating ACE and LOMI systems, including UI, database, and automation components. Highlighted the validation bundle responsible for checking user requests and stopping the process if errors occur.

• Validation Details and Exception Handling  
  Clarified the difference between business exceptions (invalid user requests) and system exceptions, with both requiring the process to stop. Emphasized backend validation alongside UI validation to prevent duplicate or invalid entries, especially for use case names and team registrations.

• Team and Use Case Data Handling  
  Discussed handling new and existing teams, maintaining JSON payloads as-is for group emails, and saving additional properties like team name and use case name. Explained that use case IDs dictate whether certain fields are mandatory and how distribution lists are fetched or bypassed accordingly.

Automation and Scheduling of Rule Processing

• Rule Execution Scheduling and Email Notifications  
  Discussed running the rule processing at 12 AM instead of 10 PM to avoid missing late entries. Emphasized the need to send daily emails to the tech team even if no new rules are registered, to avoid manual checking.

• Data Validation and Result Updates  
  Explained the process of executing rules, validating results (pass/fail/error), and updating the DQ artifacts table with actual values, expected values, SQL queries, and execution status. Highlighted the importance of saving generated SQL queries for future review and modification.

• Automation Workflow and Task Management  
  Described the creation of human tasks after rule creation, notification emails to partners, and the workflow for tech team members to reserve, implement, and complete tasks. Clarified that rejected rules stop the process without creating tasks.

UI and API Requirements

• API for Track My Request and Approver Pages  
  Discussed APIs to fetch team-specific or all-team data for different user roles. Explained pagination and filtering based on team or use case ID. Clarified differences between approver and track my request pages and their data scopes.

• UI Enhancements and Role-Based Access  
  Planned a new page for the tech team to manage onboarding tasks, visible only to tech roles with a new "super admin" role introduced. Discussed enabling/disabling edit buttons based on approval status and integrating approval/rejection flows.

Error Handling and Future Enhancements

• Access Issues and Error Capturing  
  Highlighted the need to capture errors related to service ID access to tables during query execution. Proposed triggering emails to request access when such errors occur, improving communication with partners and tech teams.

• Configuration and Query Management  
  Decided to define project and dataset IDs in the local configuration rather than referencing monitoring tool configs. Discussed replacing placeholders in SQL queries with actual values before execution.

• Review and Next Steps  
  Sachin mentioned upcoming review with Rajendra and possible design tweaks. Assigned automation leadership to Nirmal and noted bandwidth considerations for task assignments. Emphasized sharing updates on the channel and preparing for a demo on Monday.
