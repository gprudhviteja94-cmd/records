📒Meeting Outline


Airflow tag monitoring & QTrak data monitoring tool

  • Access & initial checks The presenter shared their screen and confirmed attendees could access the production monitoring pages (Airflow and QTrak). The workflow for initial access was explained: open the QTrak monitoring page, add a filter (execution day / free text), refresh to see tags for the selected date. The filter limits the view to a particular column and execution date (e.g., today, 5th).

  • Finding and inspecting a tag Walkthrough of selecting a tag: copy the tag name from QTrak, search that tag in the QTrak UI to view its configured schedule, tasks, DAGs, and the list of DQ (data quality) rules associated with that tag. The presenter demonstrated opening the tag in the production Airflow UI, where the DAG for that tag populates automatically after pasting the DAG name.

  • Interpreting DAG/task status In Airflow, the DAG tasks on the left display color-coded status: green = success, red = failure. Green indicates the related database data updates happened for the given date. Red indicates a failure that requires attention. The presenter emphasized that DAG-level failures require immediate action; individual failing DQ rules may not always require immediate escalation.


Querying BigQuery for DQ results

  • Constructing the verification query The presenter showed the BigQuery console and explained how to construct a SELECT query to verify the DQ results for the tag on the execution date. Required inputs: table name (available in the QTrak config and UI), list of DQIDs (use IN operator with all rule IDs for that tag), and the execution date filter (e.g., today’s date). The presenter ran the query to show the 16 DQ rules and their results for the chosen date.

  • Interpreting query results The query returns rows for each DQ rule for the date. Important columns include pass/fail status and whether data exists. Sometimes a rule will show “no data” (e.g., only 15 rows rather than 16) which is expected when no records were produced for that rule/date. When all returned rows are passing, monitoring confirms the tag passed for the day.


Notifications, escalation, and actions

  • Email notifications The DAG ID/tag is used to search the email inbox for the daily notification. The team receives emails for both success and failure, and the monitoring process requires checking those notifications as part of end-to-end validation. If everything passed, the team sends a summary message stating no failures for that tag that day.

  • Failure handling and partners If a DQ rule fails, the failure details (e.g., check type and observed value) are included. For threshold checks, the example showed an expected range [-10, 10] and an observed value -11 causing failure. When failing rules occur, partner email addresses are included for escalation in some failure types. Only certain failure types (and DAG failures) are escalated to partners; routine DQ rule failures may be handled internally.

  • DAG failure vs rule failure The presenter clarified the difference: a DQ rule failing is not always critical, but a DAG showing red (task/graph failure) indicates a larger problem requiring immediate attention. DAG failure indicator: the DAG view shows a red state for tasks or an overall red representation in the graph.

  • Rerun and remediation process If a DAG or critical failure occurs, the team first informs Sachin (or the designated owner) to decide whether to re-trigger the DAG or take alternate actions. Possible root causes for failures include infrastructure issues, numerator/denominator data inconsistencies, or code/configuration errors. For reruns, the team waits for guidance from Sachin before re-triggering.


Access, training, and assignment

  • Required access Cloud console (BigQuery) and Airflow access were identified as mandatory for monitoring tasks.

  • Training & ramp-up Manmohan asked questions and was provided KT (knowledge transfer) during the call. The presenter said initial monitoring assignments are limited to allow ramp-up; responsibilities will expand as members become proficient. A Confluence production-issues tracker was created and should be used to log production incidents.

  • Supporting materials The presenter offered to share sample query snippets and the SELECT schema/query used for verification if anyone needs details or examples.


Miscellaneous

  • Attendees were encouraged to reach out if query results do not display as expected or if they need further clarification.
