📒Meeting Outline


Onboarding data flow and artifact table

  • UI → artifacts table The UI (developed by Kundan and Athar) captures business requests (use case, table name, column name, where clause, frequency, focus metric). After business verification (Anand and team), approved entries are pushed into the artifacts table. That “push” step (integration between UI and artifacts table) is being developed separately and not finished yet.
  • Artifact record fields & semantics The artifact entries include: use case id/name, table name, column name, where clause, TS (timestamp/run date), frequency (daily/monthly), and focus metric (average/mean, count, median). If focus metric is not provided, code defaults to mean-related calculations (mean, stddev, skewness).
  • Clarifications requested / expectations New team members should start by reviewing front-end and artifacts table contents to understand the incoming records and data shape before diving into backend code.


Onboard metric creation (12-month baseline)

  • High-level process For each artifact record, the onboarding pipeline aggregates the focus metric for a baseline period (12 months by default). It computes an aggregated time series: timestamp and value pairs (periodal averages/metrics).
  • Computed statistics and derived signals The onboarding computes mean, population standard deviation, skewness, and rolling aggregates called AC7 and AC30 (7-day and 30-day lag/rolling derived metrics). AC7/AC30 are computed using lagged values (previous 7 or 30 points) — code contains the specific logic for computing these.
  • Primary method selection Using AC7, AC30, coefficient of variation (CV), and skewness, the code selects a "primary method" for thresholding per metric. The primary method determines how thresholds (lower/upper bounds) are set.
  • Threshold creation and storage Based on the chosen primary method, the onboarding process creates lower and upper thresholds and stores them in the profile/threshold table (profile metric table). Each metric gets a metric_id (unique per metric and timestamp). Parameter JSON and other metadata are populated and stored into the repository (DQ repository / GQ repository).
  • Multivariant support Multi-variant logic exists in schema/response but is not enabled in current code — returns null presently. Multivariant onboarding will be implemented in upcoming sprints (3rd/4th sprint).


Daily/monthly monitoring and DQ runs

  • Routine runs Once onboarding builds a 12-month baseline and thresholds, daily/monthly monitoring runs are executed. The monitoring job aggregates metric values for the target window (e.g., last day for daily runs) and compares the aggregated value to the previously generated lower/upper thresholds.
  • DQ results / pass-fail logic Comparison results (pass/fail / positive/negative) are recorded into the DQ results table (DQ repository). The team has completed much of this and is performing post-testing and demos; code may need adjustments after demos.
  • Threshold revision (monthly aggregation revision) Requirement: periodically (monthly) recompute thresholds by re-running the 12-month aggregation using the latest data (sliding window). If new thresholds differ from existing stored thresholds, update the profile/threshold tables accordingly. This ensures thresholds evolve (e.g., by month the 12-month window shifts one month forward, so thresholds may change). The speaker is currently implementing and testing this revision logic.

📋Overview

  • Business submissions are collected via UI and, after approval, inserted into the artifacts table for onboarding.
  • Artifacts contain required fields: use case, table, column, where clause, TS, frequency, focus metric.
  • Onboarding computes 12-month aggregated metrics (timestamp + value pairs) and derives mean, stddev, skewness, AC7, AC30.
  • Primary method selection uses AC7/AC30/CV/skewness and decides thresholding approach.
  • Thresholds (lower/upper) are stored in profile/threshold table with metric_id and parameter JSON.
  • Multi-variant support is present in schema but not implemented yet (scheduled in future sprints).
  • Daily/monthly runs compute recent aggregated metric and compare against thresholds to produce DQ results.
  • Monthly revision requires recomputing 12-month baseline on a rolling window and updating thresholds if changed — this work is in progress.
  • New developers should inspect UI artifacts, DB schema, and onboarding code, and run code to understand outputs. Collaboration and follow-up sessions encouraged.
