📒Meeting Outline

Data Quality and Record Handling

• Handling of Duplicate, Stagnant, and Missing Data  
  The team agreed to provide only one sample record per standard description type to Rajna for review. Duplicate and stagnant data issues have been resolved, but missing values remain a problem and will be shared for further action. Duplicate records should not be sent, and stagnant records are mostly addressed except for some complex cases. The focus is on sharing valid value checks and ensuring no redundant data is sent.

• Valid Value Checks and Input Template Limitations  
  Discussion highlighted the complexity of valid value checks due to multiple data types and conditions (e.g., date ranges, string patterns, lengths). The current input template is simplistic and does not cover all possible validation combinations. Modifying the template to accommodate dynamic and complex validations would require significant changes, and a decision was made to revisit this after further analysis.

Timeliness and Stagnant Data Checks

• Clarification on Timeliness Check vs. Stagnant Data Check  
  Timeliness checks are essentially a subset of stagnant data checks focusing on data freshness (e.g., data or model refresh within the last 45 days). Most stagnant data checks have been renamed or reclassified as timeliness checks except for about 10% that are complex and cannot be handled via UI forms. These complex checks will be managed through a control route and are excluded from the current UI dropdown options.

• SQL Query and Check Type Implementation  
  The team discussed the need for clear SQL query templates for timeliness checks. It was clarified that the timeliness check is present in the current system but may not be explicitly labeled as such in all repositories. Migration efforts will focus on the simpler timeliness checks, while complex stagnant checks remain out of scope for form-based input.

Data Migration and Testing Concerns

• Use of Production Data for Migration and Testing  
  Strong concerns were raised about the current practice of not pulling data directly from the production environment for migration and testing. This has led to invalid or incomplete data being used, which risks embarrassing the team in front of product owners. The expectation is that migration should always use production data, and testing should validate with real-time data to avoid rework and delays.

• Responsibility and Accountability  
  Senior team members were reminded of their responsibility to ensure data quality and proper procedures. The reduction of deprecated DQIDs from 1300 to 900 was acknowledged, but basic validations and data sourcing must be improved. Feedback on data issues will be escalated through Purna to Rajendra, emphasizing the need for ownership and proactive communication.

• Impact on Project Timeline and UI Modifications  
  The delay caused by data issues affects the overall tool migration timeline. The team is cautious about making UI changes and prefers to ensure data correctness first. Concerns were raised about potential consequences if data does not reflect correctly in the UI after migration, stressing the importance of thorough validation and clear understanding of check types.

• Communication Gaps and Expectations  
  The meeting highlighted a lack of proactive communication, especially regarding the timeliness check use case and SQL requirements. Team members were encouraged to voice questions and concerns openly rather than remain silent. The need for clarity and collaboration was emphasized to avoid misunderstandings and ensure smooth progress.
