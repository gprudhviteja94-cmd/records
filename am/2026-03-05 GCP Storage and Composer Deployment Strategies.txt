📒Meeting Outline


GCP Storage & Composer Deployment

  • Access to BigQuery table and environment The team confirmed that access to the BigQuery table is available from the E1 environment after deployment. Deploying to E1 will make the resources accessible without additional manual authentication.

  • Where to store generated SQL and Python files Discussion focused on where to keep generated SQL files and supporting Python code. The recommendation is to upload files to the project’s GCS bucket (Cloud Storage) that is tied to the Composer environment. A specific bucket path (project/Composer bucket) was shown during screen share; files can be placed in an existing folder or a newly created folder inside that bucket.

  • Local vs environment-level authentication When executing from the environment (Composer/E1), DAG/composer maintains authentication and connections automatically; no manual auth is required. For local development, developers must authenticate locally and create needed connections.

  • Bucket path details & file placement The presenter showed the Composer environment tab and Cloud Storage bucket contents. The bucket contains various files and folders; developers can upload Python and SQL files directly into the bucket. If unsure about exact folder, team members can request the specific path or create a new folder under the project bucket where the team has access.


Composer Behavior & Deployment Workflow

  • Composer auto-deploy / syncing behavior Composer auto-deploys files present in the bucket into DAGs. In lower environments (like E1/dev), uploading files directly to the bucket is enabled (upload UI enabled). For higher environments (E2, E3), direct upload is disabled and files must be deployed via the formal deployment pipeline (Git sync / CI).

  • GitHub sync and planned workflow There is an intended plan to sync Composer bucket with GitHub, but that capability is not yet enabled (limited bandwidth/priority). Currently Composer can copy files from GitHub to the bucket in some setups, but for immediate testing the recommendation is direct upload to the E1 bucket.

  • Testing workflow on E1 For validation/testing on E1, upload the Python files (one or many) or a folder containing files to the Composer bucket. Composer will parse the Python DAGs and the corresponding DAG IDs will appear in the Airflow UI. If E1 is not currently synced, placing files directly in the bucket ensures they are available for validation.

  • Files count and folder upload The upload UI supports multiple files and folders — you can place many files together in a folder. Once uploaded, the DAG(s) created from those files should appear in Composer/Airflow UI according to their DAG IDs and tags.


Troubleshooting & Next Steps

  • If DAGs don’t appear If uploaded DAGs do not show in Airflow UI, verify:
    
    • Files are in the correct project bucket tied to E1 environment
    • Folder structure and file names are correct and DAG code syntax is valid
    • Refresh/lookup by DAG ID or tag in Composer UI If still failing, escalate or ping the E1 admin for checks.

  • Testing vs production deployment For development/testing use direct upload to E1 bucket. For higher environments (E2/ E3) and production, follow the formal deployment pipeline (Git-based deployment) when it becomes available.

  • Local runs require manual authentication and connection configuration; environment-level runs do not.
  • Direct upload is enabled for lower (dev/E1) environments; E2/E3 require formal deployment (Git/CI) and currently sync with GitHub is not enabled.
