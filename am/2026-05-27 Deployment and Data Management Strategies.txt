📒Meeting Outline

Deployment and Environment Management

• Email Notification on E3 Deployment  
  It was emphasized that email notifications should only be sent when deploying to the E3 environment. The distribution list must be temporarily changed to the internal team during deployment validation and then reverted to the partner's email after validation. Sachin confirmed responsibility for this task.

• Data Saving and Deployment Restrictions  
  It was confirmed that no data is being saved to any tables during deployment. A3 environment deployment is to be avoided on the current day and Friday. UAT approval is mandatory before deploying changes to the ETH environment to prevent unauthorized RFC creation. Product team sign-off is required even for minor changes.

Data Handling and UI Functionality

• Data Transfer and Reuse in DAG Tasks  
  Discussion on transferring data from cluster to DAG tasks concluded that data reuse is feasible and has been implemented. Future use cases will be planned, possibly extending calls to one hour for knowledge sharing.

• UI Macro Integration and Status Filtering  
  The UI macros have been integrated with renamed headers and classification values. Conditional checks are handled in backend code, allowing blank values without issues. Users must filter data by status (e.g., "open") manually, as hardcoding status filters is discouraged due to potential future changes. Pagination and component data passing challenges were noted, with possible use of context API for data flow.

Data Transformation and Policy Setup

• Transformation and Execution Policies  
  Nirmal and Kundan were tasked to create transformation and execution policies for processing Excel sheets in the ACE Control Center. They are to connect and understand the policy concepts thoroughly.

• DQ Table Changes and Impact  
  Any changes to the DQ table should be communicated promptly. The current process involves fetching data and generating Excel sheets, with attention to data types (string, boolean, integer).

Data Migration and SQL Optimization

• Hold on Data Migration Due to Description Updates  
  Data migration is paused because description updates are ongoing to support 50 use cases.

• Handling IA Code Data Without Creating Tables  
  It was discussed that the current table storing IA codes and non-MR IA codes is not uniform and lacks meaningful relationships. The recommendation is to remove filtering conditions from SQL queries and instead perform filtering in Python code using dictionaries and lists for better maintainability and performance.

• Table Creation and Metadata Recommendations  
  Instead of one mixed table, two separate tables should be created: one for MR IA codes and one for non-MR IA codes. Each table should include metadata columns such as created by, created timestamp, updated by, and updated timestamp to maintain data lineage. Soft delete is not required; hard deletes will be used.

• SQL Query Optimization  
  Developers are encouraged to optimize SQL queries by reducing joins to improve performance while ensuring results remain consistent.

• Next Steps for Table Creation and Data Population  
  Once tables are created, Suman should be informed. Initial records can be inserted for testing, with the remainder populated later. Script modifications will be needed to accommodate these changes.
