📒Meeting Outline


Q-Track (Data Quality Monitoring Tool - overview & alerts)

  • What Q-Track is Q-Track is a data quality monitoring tool (dashboard + automation) that runs predefined rules on BigQuery tables (example: USCDO/USCFO tables). Rules are configured per table/column and run on a schedule; results are persisted and automated alerts are generated when rules fail.

  • Rule examples and behavior Examples explained:
    
    • Primary key uniqueness: if a RESI_user_id duplicate appears, an alert is generated.
    • Non-null constraint: if bonus_amount is null when it should not be, an alert is generated.
    • Threshold/percentage checks: e.g., count of future dates should not exceed 5% of total; expected value 0.05 vs actual triggers failure.
    • Valid-value checks, missing-value checks (100% field-rate), stagnant checks, etc. The presenter explained how business statements (intake form) translate to SQL checks and how expected vs actual values determine pass/fail.

  • Data sources & scope Q-Track rules run on the table after ingestion; it does not track which upstream source supplied the data. Rules are table-level or column-level; a single table can have multiple rules.

  • Notifications When a rule fails, an automated email alert is sent to the business distribution list (table owners / business users). Emails are system-generated by the automation; team does not manually compose these. Pass results are stored for monitoring but do not trigger business notifications (except internal monitoring).

  • DQ repository & results storage
    
    • Rule definitions (DQ rule ID / model ID) are stored in a DQ repository table (master).
    • Execution results (pass/fail, actual/expected values) are written to a DQ results table.
    • The implementation scripts read rules from the repository, execute queries, store results, and trigger alerts based on results.


Q-Track UI (Issue Management / Human Tasking)

  • Problem addressed A high volume of daily email alerts makes manual triage difficult. Q-Track UI (also called DQMI / issue management) centralizes failed results so users can take action without sifting through many emails.

  • Daily processing & human task creation
    
    • At end of day, the automation aggregates the DQ results produced that day (e.g., 100 results).
    • The downstream process ingests all results; for passed items no action is required.
    • For failed items (e.g., 10 fails), the system creates “human tasks” in the Q-Track UI — one task per failed rule — so users can triage them.

  • UI workflows / possible actions
    
    • Users can view failed records, open details, reserve/assign tasks (to avoid duplicates across a distribution list), add comments, request rule deletes/modifications, or mark whether the failure is a true data issue.
    • If the failure is a true data incident, the UI can create a ServiceNow incident (or similar ticket) to route to support/engineering for remediation.
    • If the rule itself needs revision or deletion, the user can request changes (which then go through product/PO approval).

  • Users of the UI
    
    • Intended users are business/table owners and teams responsible for data quality. They will triage and mark failures as expected or requiring action.
    • The UI is not only for internal infra team; business users will also use it to review failures rather than rely solely on email.


Q-Track Reporting (Monthly / Quarterly Reporting & Trends)

  • Purpose Reporting visualizes rule run statistics over time for leadership and stakeholders: unique rules executed, pass/fail counts, trends, pass/fail ratios, and lists of frequently failing rules.

  • Data & visuals Reports will be based on historical DQ results (e.g., last 12 months), showing trend analytics and rule-level breakdowns. This helps leadership see overall data quality health.


Q-Track Self-Serve / Onboarding UI (in discovery)

  • Goal Provide a UI where business users can submit new DQ rules via a guided intake: select use case, table name, check type, variables, filter conditions, expected values, frequency, etc.

  • Flow
    
    • User fills intake fields (the intake form is currently an Excel template in use).
    • Submitted rule creates a rule definition in the DQ repository (DQ rule ID auto-generated).
    • Rule goes through approval (product/PO) before being deployed.
    • Planned capability: allow users to modify existing rules or create new ones from the UI. The design/discovery is in progress.

  • Advanced possibility (planned) Exploration of generating SQL queries automatically from the user-provided rule description (agentic tool). This is in discovery; implementation not started.


Controls & Rule Efficiency (future initiative)

  • Control analysis A control initiative will evaluate how effective existing rules are against changing data distributions and may modify or adjust checks automatically (in pipeline / implementation stage). This aims to keep rules relevant as data evolves.
