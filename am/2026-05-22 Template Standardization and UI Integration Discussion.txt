📒Meeting Outline

Template Configuration and Standardization

• Unique Set of Templates  
  The discussion focused on understanding the unique set of templates used for various data quality checks, such as missing value checks, stagnant checks, duplicate checks, and valid value checks. It was clarified that although multiple rules exist under a single check (e.g., 20 rules under missing value check), these correspond to one template. The need was expressed to obtain a standard, unique set of templates with their corresponding template numbers and descriptions for easier reference and usage.

• Template Number and Description Mapping  
  The team reviewed how template numbers map to multiple descriptions. For example, stagnant 1 maps to four different descriptions, but these descriptions are essentially similar or variations of the same rule. Clarification was given on how certain terms like "00" and "similar" are handled distinctly in the descriptions and variable conditions.

• Total Number of Templates  
  The total number of templates was estimated to be around 35 to 40, distributed across different checks: stagnant (3 templates), duplicate (2 templates), missing value (14 templates), and valid value check (13 templates). The missing value check has the largest number of templates.

Integration with User Interface (UI)

• Challenges with Description Combinations in UI  
  Concerns were raised about the complexity of handling many description combinations in the UI, as the UI may not support creating so many variations easily.

• Proposed UI Solutions  
  Suggestions included providing a dropdown or semantic search box for users to select from predefined descriptions mapped to templates. Users could then edit the description if needed. This approach aims to balance flexibility and standardization.

• Auto-Generated Descriptions and User Input  
  It was noted that currently, descriptions are auto-generated based on input fields, which may cause issues if users enter incomplete or inconsistent information. To address this, the team discussed separating description content from input parameters and moving some description details into filter criteria or other UI input fields.

Streamlining Description Usage and Backend-Frontend Sync

• Reducing Dependency on Descriptions  
  The team considered minimizing the use of descriptions in the backend configuration by extracting key parameters (e.g., column names, conditions) directly from input fields rather than relying on parsing descriptions.

• Moving Description Data to Variables  
  It was proposed to move data currently embedded in descriptions into dedicated variables or filter criteria fields, which would simplify both backend processing and frontend UI design.

• Backend and Frontend Alignment  
  The current backend configuration includes descriptions that the frontend does not fully utilize, as the frontend collects parameters separately. The plan is to align backend and frontend by reducing description usage and relying more on structured input fields.

• Next Steps for Implementation  
  The team agreed to review which templates require changes to move data out of descriptions and into variables. The changes are expected to be manageable and will be communicated as needed.

📋Overview

• The team clarified the need for a unique, standard set of templates with template numbers and mapped descriptions for all data quality checks.
• It was confirmed that multiple rules under one check correspond to one template, with some templates mapping to multiple similar descriptions.
• The total number of templates is approximately 35 to 40, with missing value checks having the most templates.
• Challenges in integrating many description combinations into the UI were discussed, with solutions proposed such as dropdowns or semantic search for description selection and editing.
• The team plans to reduce reliance on auto-generated descriptions by moving key parameters into structured input fields and filter criteria, improving backend-frontend synchronization.
• Implementation of these changes will be reviewed and executed, with communication on any exceptions or special cases.
