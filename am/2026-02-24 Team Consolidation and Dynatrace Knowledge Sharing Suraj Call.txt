Dynatrace knowledge-sharing session

  • Purpose & placement Dynatrace was presented as the observability tool in the Hydra Cloud Platform stack (Hydra = wrapper over OpenShift/Kubernetes). It provides 360-degree visibility — logs, metrics, and traces — for the platform and applications.

  • Architecture & data flow The presenter explained the infrastructure stack: data center/cloud → hosts (Kubernetes worker nodes) → pods → containers → processes (Java/Spring apps) → services (API endpoints). A Dynatrace agent is installed to auto-instrument and collect telemetry (logs, traces, metrics) and send it to the Dynatrace cluster.

  • Accessing Dynatrace Access via the Hydra console → Application Launcher → select environment → Dynatrace landing page. The landing page shows high-level issues, request counts, response times, JVM/.NET/Go metrics and links to services.

  • Service & request views The services view lists running services, endpoints, request counts and response metrics. You can click into Web Requests and drill down to individual services and endpoints. Filters (region, service name, etc.) help narrow views.

  • Distributed tracing Distributed traces show the request journey across services: security filters → controller → service → DB calls → events → response. Each span/step is recorded; tracing context is propagated across services (OpenTelemetry will be explained in detail in a future session).

  • Multi-dimensional analysis The tool provides a multi-dimensional analysis/diagnostic view to correlate metrics (CPU, memory, disk, exceptions) with request patterns. You can pick metrics and see which services/requests are consuming resources.

  • Pod-level vs service-level Demonstration included examining a specific pod to view response time, failed requests, throughput, events, and pod logs (Kibana-like logs integration intended but not fully configured). Emphasis by presenters (and reinforced by a colleague) that pod-level investigation is often more actionable than service-level for debugging, while aggregation across pods/services is available via multi-dimensional analysis.

  • JVM & System metrics There was a focused walkthrough of system metrics and JVM metrics (GC activity, memory regions like ZGC/old gen, thread counts). These are key when doing load testing and performance analysis.

  • Tracing & logging integration Dynatrace captures logs and traces; there is a separate ELK/ELF pipeline/UI for logs — more detail will be covered later. The presenter confirmed that tracing correlation is done via context propagation (HTTP headers) and OpenTelemetry instrumentation.

  • Follow-ups requested Requests were made to show:

    • Standard thresholds and configuring events/notifications/alerts — presenter to gather and present info in a future session
    • How to aggregate metrics to service/project level (use multi-dimensional analysis with correct filters)
