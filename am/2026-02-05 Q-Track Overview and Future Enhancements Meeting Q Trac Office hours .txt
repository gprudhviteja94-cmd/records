📒Meeting Outline


Q-Track overview & history

  • Purpose and origin Q-Track is a data quality monitoring (DQM) and anomaly detection tool launched Aug 2023 to provide data quality capabilities to non-Calibrate users across the enterprise. It addresses needs for data producers, analysts and use-case teams to run quality checks and log outcomes without requiring Calibrate steward access.

  • Problem statement solved Q-Track centralizes detective data quality checks and incident logging for process-level metrics (joins across tables and derived metrics), ingestion checks, and column-level checks where applicable. It addresses the need to place and log DQ checks per MRFG standards and to create an auditable history of incidents and remediation.

  • Timeline and scale Ideation began Dec 2022; initial build in 2023. Grew to 1,000 TQ rules in 2024. Migration from Cornerstone to Ruby completed late 2024. Current footprint: ~2,000 rules across ~50 tables (30% coverage of USCIS inventory).

  • Architecture & tech stack
    
    • SQL-based checks run in BigQuery (queries and logic live in BigQuery).
    • Orchestration via Airflow tags in GCP; scripting in Python.
    • Hosted environment moved from Cornerstone to Ruby.
    • Alerts delivered by email only when checks fail.
    • New Data Quality Incident Management (DQI) portal added for governance and incident logging.


Capabilities & types of checks

  • Types of checks supported
    
    • Threshold checks (numeric ranges or percentage thresholds)
    • Valid value checks
    • Missing value checks
    • Stagnant data checks
    • Duplicate checks
    • Ingestion checks (detect missing or late ingestions)
    • Process-level checks (complex joins/derived metrics that represent business processes)

  • Current scope All checks are detective (post-ingestion). Q-Track does not block ingestion; it detects and alerts after data is loaded.

  • Alert content Alerts include table name, variable name, frequency, description, expected vs. actual values, and run timestamp to support investigation.


Governance, incident management & reporting

  • DQI portal purpose The DQI portal centralizes alert triage, partner analysis and remediation workflows so conversations and decisions are logged and auditable (Project Guardian compliance). It replaces ad-hoc email/chatter-based communications with structured tracking.

  • Reporting cadence
    
    • Monthly: consolidated pass/fail counts per check, per use case; trend plots of failures across time to support monthly review.
    • Quarterly: aggregated DQI reports summarizing incidents, variables/tables tracked and broader impacts.

  • Remediation workflow
    
    • Alert fired -> recipient receives email -> partner reviews alert and records classification in DQI (false positive or true positive).
    • False positives: partner options include Delete rule, Monitor rule, or Revise rule (with justification).
    • True positives: partner records impact (number of customers, dollar impact) and classifies the incident. An incident (ServiceNow INC) is automatically created and routed to production support; remediation and triage begin with production and table owners. Incident number will be linked back in Q-Track for status tracking.


DQI portal demo & user workflow

  • Portal access & filtering
    
    • URL: aceworkspaces.axb.com (SSO group access shared in chat).
    • Users can filter by workbasket (use case), status (open/in-progress/closed), table, variable and other attributes to see only their alerts.

  • Alert handling on portal
    
    • View alert details (expected vs actual, run date, description).
    • Log analysis and choose classification:
      • False positive -> choose Delete / Monitor / Revise + justification.
      • True positive -> provide impact metrics; system creates ServiceNow incident and notifies production support.
    • All entries (classification, justification, and action) are logged in DQI for audits and retrospective analysis.

  • ServiceNow integration
    
    • True positive submissions produce a ServiceNow incident (INC) with details; the incident is sent to the respective data team. Q-Track will include a hyperlink from the alert to the ServiceNow INC for tracking remediation status.


Roadmap & planned enhancements (2026+)

  • Self-serve onboarding portal
    
    • Explore page to browse existing checks by use case/table.
    • New rule intake forms on UI replacing Excel intake sheets.
    • Goal: enable partners to submit checks, accelerate onboarding and reduce time-to-deploy.

  • AI / ML capabilities ("One Rule" / intelligent thresholds)
    
    • Historical profiling (6–12 months) to compute profile metrics: autocorrelation, coefficient of variation, skew, distribution shape.
    • An algorithm selector chooses among ~7–8 algorithms to generate more accurate thresholds, adapting to data characteristics (seasonality, sparse/repeating values, skew).
    • Periodic re-profiling (monthly/6/12 months) to adapt thresholds as data drifts; supports univariate and planned multivariate analysis to account for correlated variables.
    • Expected result: fewer false positives, better threshold fit, automated threshold recalculation over time.

  • AI-assisted self-serve
    
    • After minimal input (table, variable, filters), the UI will recommend relevant DQ checks and suggest rule definitions (AI-enabled). Partners can accept recommendations and deploy quickly (target: rapid deploy, e.g., 24-hour target to deploy once approved).

  • Expanded coverage & acceleration
    
    • Expand DQ coverage across more datasets and platforms within USCIS using AI-assisted creation of checks for Critical Data Elements (CDEs).
    • Automated and improved visualizations in reports (seasonality plots, trend visuals) so partners can more quickly assess impact.


Clarifications & Q&A highlights

  • Q-Track is not intended to replace Calibrate; it complements Calibrate by enabling broader non-steward users to place checks and manage incidents. Calibrate remains the enterprise tool for stewards.
  • Checks are currently detective only; future capabilities may expand automation around sign-off and onboarding but not stated as preventive ingestion-blocking.
  • Thresholds can be numeric, percentage, ranges, or derived from joins/complex logic. The ML framework improves thresholds beyond single-method approaches (e.g., interquartile range).
  • Current intake remains Excel -> Q-Track team -> tech deployment. Self-serve UI will remove Excel and enable direct onboarding and AI improvements.
  • Impact capture (dollars, number of customers) will become structured via dropdowns to help severity assessment and prioritization.
