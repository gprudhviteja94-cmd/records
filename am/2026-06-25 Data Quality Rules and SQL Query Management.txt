📒Meeting Outline

Data Quality Rules and Dynamic Date Handling

• Dynamic Date Replacement in Rules  
  Discussion focused on making date values in data quality (DQ) rules dynamic, replacing static dates with current dates or dates relative to the current date (e.g., past one month). It was agreed that dates should not be hardcoded but dynamically handled in the rules.

• Basic Checks and Missing Value Threads  
  The team confirmed that basic checks such as ensuring variables are not null and validating missing values should be applied over a recent time window (last one month). These checks are straightforward and essential for data quality.

• Conversion to Latest Template  
  Rachna confirmed plans to convert existing rules to the latest template developed by Prithvi. However, some complex rules, especially those involving multiple filter conditions and inner queries, may not fit neatly into the template.

Complex SQL Queries and Filter Conditions

• Handling Multiple WHERE Clauses  
  The team discussed SQL queries with inner and outer WHERE clauses, particularly those parsing dates to validate formats (e.g., yyyy-mm-dd). It was noted that multiple WHERE clauses are valid in nested queries, but combining them into a single WHERE clause with AND conditions might simplify the logic without changing results.

• Automation and Python Code Generation  
  It was clarified that most SQL queries are generated via Python code developed by Charami, not manually written. This allows flexibility in modifying queries as long as the logic remains correct.

• Validation and Testing of Converted Queries  
  Sachin and others emphasized the need to validate the converted queries by comparing outputs and ensuring no syntax errors. They also stressed avoiding the use of SELECT * in queries, especially due to the presence of PII data, recommending SELECT COUNT on relevant fields instead.

Data Validation and Rule Testing

• Duplicate Records and Query Accuracy  
  Nancy shared findings on duplicate record checks where some alerts were triggered incorrectly due to differences in certain columns. The team agreed on the importance of back-casing failures by examining exact records to confirm if they are true duplicates or query issues.

• OR Conditions and Null Values  
  A specific case involving OR conditions and null values in event timestamps was discussed, highlighting that such findings indicate the rules are working correctly by identifying real data issues.

• Rule Deployment and Description Updates  
  It was agreed that rules validated so far can be deployed to the E3 environment for testing. Descriptions for these rules will be updated later after alignment with Ashwin. Until then, current descriptions can remain as is.

Coordination and Next Steps

  Sachin highlighted that some records (64 noted) could not be mapped to existing or new templates due to significant differences, indicating that further changes are needed. The team agreed to review these cases in the upcoming ATM call for detailed discussion.
