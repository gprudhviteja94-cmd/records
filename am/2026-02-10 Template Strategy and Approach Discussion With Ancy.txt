📒Meeting Outline

Template strategy and approach

• Need for analysis before coding  
  The group agreed that extensive analysis of HTLS and existing SPL/SQL patterns is necessary before writing code. Coding is considered straightforward and quick compared with the design work; the priority is to identify and define templates that cover the variety of real-world cases.

• Create multiple base templates with placeholders  
  Instead of using simple prefix/suffix insertion, the preferred approach is to create stable base templates containing placeholders. A script would populate those placeholders at runtime. Templates act as stable contracts that won't change across formats (JSON, SPL, etc.), enabling generation scripts to reuse templates across use cases.

• Multiple templates to cover pattern variety  
  There are many different SQL/SPL patterns (null checks, valid-value checks, ICB scripts, other domain-specific checks). Three to four templates are likely insufficient; templates should match the number of distinct patterns discovered. The team should research and catalog patterns from existing scripts to determine required templates.

• Union / Union All / Union Order considerations  
  Union and Union All were discussed as recurring constructs; Union Order (union with ordering or specific union variants) is also in use. Templates must explicitly account for union-related variants so the generated code handles those correctly.

• Avoid one-off solutions  
  A quick hack (prefix + suffix + insert query) would be trivial to implement but undesirable because it doesn't generalize. The team agreed to avoid building solutions targeting only one template or one table. The goal is a generalized generator that supports multiple templates and patterns.

Research and cataloging of existing scripts

• Review existing SPLs and SQL scripts  
  Each team member (speaker and attendees) should go through the available SPL and SQL scripts to identify differences and recurring patterns. This includes looking at manual scripts, automation POCs, ICB scripts, and other types of checks used in source systems.

• List differences and pattern types  
  Deliverable: a list of differences and the pattern types found (e.g., null-value checks, valid-value checks, count checks, union variations). This list will drive the number and shape of templates to create.

• Collaboration on template creation  
  The speaker will prepare templates and expects others to perform the same research. The team will meet again to review collected patterns and finalize template designs before coding.

Tools, prototyping and code generation

• Use of automation tools (GitHub Copilot, etc.)  
  The team may use code generation tools (e.g., GitHub Copilot) to produce code once requirements are solid. Proper, well-documented template requirements will improve generated code quality.

• Existing manual scripts and POCs  
  There are manual scripts and an automation POC already developed by the speaker. These exist but were not accepted for production deployment (not 100% deployable per Sachin). These artifacts should be reviewed as reference material but not directly adopted without generalization.

• Timing and coordination for coding  
  Coding can be scheduled after template finalization. The group agreed to take the time necessary for analysis and not rush into coding. If asked to begin coding prematurely, members should request more time to finalize templates.

Next steps and meetings

  Team members should independently review scripts and bring a compiled list of distinct patterns and representative samples. The speaker will also provide templates and SQL query patterns by the end of the day.
