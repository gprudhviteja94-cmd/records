UI: Register / Watcher / Approval flows (Review / Register update / Watch list)

  • Register update page and review queue The register update UI has two primary areas: the dequeue/alerts (task list) and register update (rules and tables). The current demo shows static data; once integration completes it will display real data. Users can search/filter by use case name and date; selecting a result shows the table with relevant values (table name, variable name, rules, watchers, actions).

  • Watcher list & adding use cases Users can view watchers (distribution lists) via an info icon to see which tables a watcher observes. The plan is for distribution lists (DLs) to populate a dropdown; users must select their DL to register a use case. To prevent arbitrary DL creation, the team discussed adding an approval step for new DLs/use cases.

  • New-use-case flow & self-registration Proposed changes: add a "Register new use case" button (and similar for DL) that allows users to submit a request when their use case or DL is not present in the dropdown. That request goes to an approval page where approvers can view full request details and approve/reject with justification. The UI will include a confirmation dialog with request details and a justification box (reason for approval/rejection). Email integration will notify requestors of decisions; backend work required.

  • UI tweaks & UX Feedback included reducing the search box size, changing certain icons to text (e.g., "Watch list"), reducing heading size, making "Add rule" / "Watch list" more discoverable, and adding pagination for large result sets. Ather demonstrated the "register your use case" flow; team asked for clearer navigation and a page where full request detail is visible before approval.


Rule creation, templates & self-serve automation

  • Automation checks & prioritization The team discussed automation checks and their current status:
    
    • Duplicate check: 1 template identified.
    • Stagnant check: 7 templates identified.
    • Valid value checks: ~114 scripts under analysis.
    • Threshold checks: ~1200 items identified; this is currently backlogged to be addressed later. Stagnant and duplicate checks are prioritized for initial automation POCs.

  • POC & roles Prithvi is building a POC for stagnant checks (seven templates) and duplicate checks. ANSI led analysis of templates with support from Prithvi and Kundan. Anthony (new team member) will enhance the UI and contribute to threshold check design once higher-priority items are in place. Team agreed to consolidate template complexity where possible so users selecting a check type (e.g., stagnant) are not presented seven different forms; rather a single form with mapped inputs. The system will generate rule descriptions; users will provide business justification and filter criteria only.

  • Template mapping & filter standardization The team agreed to standardize inputs: check type, description, and filter criteria as primary columns. Some input JSON variable mappings may remain empty for certain use cases; integration work will map these to framework fields. Missing-value logic will be handled by filter criteria (e.g., null vs percentage null).

  • Email attachments & notifications For some checks (insurance in particular) notifications must include attachments. Email-send changes and backend implementation need to support sending attachments as part of alert emails.
