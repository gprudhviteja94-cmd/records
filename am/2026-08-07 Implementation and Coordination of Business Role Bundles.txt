Implementation and Coordination of Business Role Bundles

• Bundle Implementation Boundaries and Task Creation  
  The meeting began with clarification on the boundaries for implementing the business role bundles. The team needs to build two bundles independently to avoid conflicts. The process starts from role implementation, creating tasks with parameters such as PQ root, name, table name, quality role type, and role description. The API handling these tasks is either ANSI or self-managed. Input parameters are minimal, with ADS_ID expected as an output parameter.

• Human Task Response Handling and Coordination  
  It was emphasized that the human task response handling is already implemented and should be reused. Coordination among team members is critical to avoid delays due to unavailability. The ADS ID should be retrieved from the output parameters, and the response reading should not require additional parameters. The team is expected to implement the saving of two fields: the implemented date (passed from the human task) and the assignee. If a dedicated database column for the assignee is unavailable, the data should be stored in a JSON object within the business certification block.

• Database Updates and Email Communication  
  Updates to the database should be done using the DQ rule ID as the key. The two fields (implemented date and assignee) must be saved accordingly. After updating, email communications must be sent to users. The email should include details such as rule description, actual value, expected value, table name, variable name, check type, and result. The user ID for sending emails will be retrieved from the JSON object saved during the process.

Code Optimization and Refactoring

• Code Reuse and Utility Methods  
  There is repeated code for catching human task responses involving input variables, output variables, and task metadata. A common utility method should be created to handle this, reducing duplication and improving maintainability. The team was encouraged to refactor this themselves rather than rely on management.

• Constants and Configuration Management  
  Multiple constant files exist with overlapping variables, causing unnecessary complexity. The suggestion was to merge these constants into fewer files for easier management, while still allowing logical segregation (e.g., email-related constants). Similarly, configuration classes are duplicated unnecessarily; a parent config class should be used to centralize property value retrieval, avoiding redundant business logic in context classes.

• Utility Classes and Code Structure  
  The current utility classes are scattered and inconsistent. The team should consolidate utility functions such as JSON conversion into a single utility class (e.g., bundle-util). The existing AIS utility classes should not be duplicated but extended or reused where possible.

The list API for displaying existing rules is ready, with a recent pull request submitted. Any required modifications can be done concurrently with core logic development.

• Review Process and Collaboration  
  Code reviews should be done incrementally after completing two or three bundles to avoid overwhelming the reviewer. This will ensure design integrity and timely feedback. Both Sachin and others were urged to follow this process strictly.

• Database Column Creation and Reporting  
  Column creation for assignee and implemented date will be completed by Monday when FI returns. Meanwhile, the team should add these fields to the report JSON files rather than relying on immediate database updates. This approach avoids database dependency during ongoing development. Once the ACE database is finalized, the DQR index and tables will be updated to synchronize columns.
