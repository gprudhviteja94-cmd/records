Validation Service and BPMN Integration

  • validate request form class The team discussed creating a service/class to validate incoming UI requests. This class will check that mandatory fields (as defined per human task input/output variables in the BPMN) are present and non-empty. If any mandatory value is empty or null, the service must raise a business exception and terminate the process. System exceptions (e.g., null pointer during processing) will also terminate the process.
  • Identifying mandatory fields Mandatory fields for each case are identified from the human task input/output variables and from a downloadable requirements/design document linked in the design page. The document contains templates (template 1..4) with key columns, allowed values, data types (e.g., numeric), and which fields are mandatory for each template. The service must use the provided template number in the UI request to select the correct set of mandatory fields.
  • Allowed blank/null values Some fields may be explicitly allowed to be blank or null per the requirements document. The validator must treat such fields as valid. The team emphasized reviewing the downloaded document to determine which fields allow null/blank.
  • Error handling & process flow On business validation failures, raise a business exception and terminate the BPM process. If exceptions occur, ensure the service common exception handler and existing BPM error flows are engaged. After validation succeeds, the flow should continue to the "send email" operation. The email operation must include retry functionality (retry policy) and interacts with BPM transitions accordingly.


Implementation Details and Naming

  • Service class name and repo Create the service class (suggested name: ValidateRequestForm or similar). If anyone prefers a different name, they should raise it. A branch will be created from the existing repository (no need to create a new repo). The service class will be invoked by a REST API (details to be provided later).
  • Inputs, context, outputs The service should accept all UI input parameters, validate them, and put validated values back into process/context as required. If validation fails, throw a business exception. If runtime/system exceptions occur, allow the process to be terminated by system exception handling.
  • Templates and allowed values Template-based validation: each template has its own mandatory field set and allowed value constraints (e.g., "allowed margin" numeric). There are four templates indicated; implement logic to branch validation rules based on template number provided in the request.
