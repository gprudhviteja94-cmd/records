📒Meeting Outline


Mod Shop overview and purpose

  • What Mod Shop is Mod Shop is a portal for creating and registering "mods" (reusable components). A mod can be reused by any team once registered and approved. The portal supports registering mod metadata (code name, version, description), business unit/market, repository link, Group ID, Artifact ID and code version.

  • Types of actions (mods) There are three action types:
    
    • Task: update-type operations (e.g., update address).
    • Data Provider: read operations (e.g., fetch address, card details).
    • Process: combination/stitched mod that may include multiple tasks and data providers.

  • Code/runtime support Currently Java is the supported runtime for mod code. Python is planned for future releases (expected within one or two sprints / one or two years — in development).


Registration, review and onboarding workflow

  • Registration First step is to write the code (API trigger, authentication, request/response handling, passing outputs to next tasks) and then register the mod in Mod Shop with required metadata and execution settings.

  • Review and approval Once registered, the mod goes through a review process. Registration moves the mod into Dev status. From Dev, it is propagated to E1 for testing. Submitting for approval moves it to the approver queue (Tech Admin or reviewers). After approval it becomes Active and can be deployed/executed in production (E3).

  • Onboarding Onboarding binds a mod/version to a deployment (residency) where the action will execute. The onboarding step itself goes through review. Some onboarding flags and deployment selection are visible only to Tech Admins (not Tech Users).

  • Editing and versioning
    
    • While in Dev status or inactive state, fields can be edited.
    • Once a mod is Active, it cannot be edited; instead create a new version (major/minor/patch) and submit the new version for review.
    • For urgent changes when not creating a new version, contact Tech Admin to update flags during onboarding.


Execution configuration and settings

  • Execution enabling There is an enableModExecution flag. If checked (default), the mod can be executed directly via UI. Unchecking disables direct UI execution.

  • Execution details Execution configuration includes retry counts, retry intervals, behavior on failures (e.g., escalate to human task or send mail), and other execution-level settings.

  • Input / Output / Config / Vault The registration screen allows defining input CRD, output CRD, application configuration, and vault/secret references. For input CRD you can specify labels, data types, and whether execution mode is single (manual/UI) or bulk (file upload). For app config and secrets, vault settings can be included.

  • Input data types and limits The portal supports multiple data types (string, number, boolean, date, datetime, map, object, list etc.). The date and datetime input types were noted as working; if issues occur, check the required date format. There is no known front-end limit on the number of input/output parameters. Backend limits were not confirmed and may need validation.


Execution modes and monitoring

  • Single vs Bulk execution
    
    • Single execution: enter inputs in UI and run one instance.
    • Bulk execution: download input template, populate multiple rows, upload, validate file, then execute. Validation checks types/format before execution.

  • Execution tenancy There is a Direct Execution Tenancy option visible only for certain deployment IDs configured as "bot tenancy." Non-MOD tenancies do not expose this option. Multiple tenancies support was discussed as now enabled; onboarding allows selecting a single tenancy per deployment. Future/expanded tenancy behavior may be covered in follow-up sessions.

  • Execution results and troubleshooting Executions are viewable in "all executed action" with version, time range and statuses (Completed, Executing, Failed). For bulk runs, the system reports counts: triggered, executed, failed, not-triggered. Error details are shown per row (e.g., API returned status 412 with error message). If execution fails, investigate error details (API response, payload format, date format mismatches, configuration).


Approval, production promotion, and ongoing changes

  • Promotion to production Only after reviewer approval does a mod move from Dev to Active and become available for production execution (E3). The team can test in E1 and E2 before approval.

  • Post-approval changes Active mods cannot be deleted/edited directly; create new versions for enhancements or patches and submit them for approval. Version metadata (Group ID/Artifact ID/version) can be updated when releasing a new version.

  • Support contacts For Mod Shop issues contact listed owners (VB, Method, Swetha were mentioned as support contacts).

  • Future sessions Additional hands-on / demo sessions will be scheduled to walk through new enhancements, tenancy usage, and runtime additions (e.g., Python).


📋Overview

  • Mod Shop is used to register reusable components ("mods") that teams can reuse after review and onboarding.
  • Mods have three types: Task, Data Provider, Process (stitched workflows).
  • Registration requires metadata, runtime artifact details, execution configuration, input/output CRDs, app config and vault secrets.
  • Mods move Dev → Approval → Active; testing in E1/E2 is possible before Active. Production execution requires Active state.
  • enableModExecution controls direct UI execution; can be disabled if you don't want UI-triggered runs.
  • Onboarding binds mod/version to a deployment/residency; some onboarding options are visible only to Tech Admins.
  • Input CRD supports many data types (string, boolean, date, datetime, list, map, object). Date format must match expected pattern — confirm format if issues arise.
  • Bulk and single execution modes available; bulk requires file validation before execution. Execution results and errors are visible with details.
  • Active mods require new versions for changes; Tech Admin can adjust flags during onboarding if needed.
  • Python runtime support is planned; tenancy support has been enhanced (multiple tenancies available).
