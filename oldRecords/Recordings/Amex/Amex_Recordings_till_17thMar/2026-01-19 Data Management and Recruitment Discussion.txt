Data Volume & Failure Grouping

  • 280 rules grouped into one Discussion on an example where 280 rules were grouped into a single item. Concerns raised that 280 failures looks excessively high and likely caused by test data being inserted. Rachna and others agreed actual failures should be much lower (suggested maximum ~30 if daily failures occur throughout a month). Clarified there are no intraday rules; maximum frequency is daily.
  • Multiple failure occurrences and merging justifications Suggested approach: if the same rule fails multiple times (e.g., twice) and has different descriptions/justifications, append both justifications (comma-separated or combined) rather than creating separate rule entries. Team agreed this is acceptable to avoid excessive duplication.


Justification & Outcome Classification UI/Flow

  • Fields required from UI Clarified required fields: justification (text), outcome classification (true positive / false positive), and sub-status (delete rule / revise rule / monitor / modify rule). The flow: user selects outcome classification, then provides justification and selects sub-status.
  • Justification visibility and requirement Decision: always show a justification text box (including for false positives). Users must provide justification when selecting any outcome (delete, revise, monitor). Athar and Kundan were requested to add the justification text box for false positive selection. Team agreed to make justification mandatory and ensure drop-downs have sensible defaults (e.g., default outcome = positive) and validation that required fields are filled before submission.
  • Hierarchy and conditional fields Discussed not making justification conditional (i.e., always present) to ease user experience and downstream processing (Atik’s work). Sub-status is considered a child field of outcome classification (sub-status appears based on outcome selection) but justification remains common.

Daily vs Onboard Metric Computation (DQ repository / Artifacts / Thresholds)

  • Role of Artifacts table vs DQ repository Clarified process: artifacts table is only a temporary staging for user inputs from UI (initial onboarding). Once onboarded, main processing uses the DQ repository (DQ repo) which stores the metric configurations (table name, variable name, focus metric, algorithm selection, etc.). Artifacts are not used in daily run.
  • Onboard metric flow Onboard metric job: determines best metric and algorithm, runs historical data (6/12 months) against the source table, computes aggregated statistics (mean, stddev, skew, min/max, etc.), and inserts thresholds (lower/upper bounds) into threshold table in DQ repo.
  • Daily run flow Daily process should:
    • Read each metric configuration row from DQ repository.
    • Based on focus metric (mean/count/median/etc.), parameterize and execute the appropriate aggregation query for the day (e.g., yesterday to today).
    • Retrieve the aggregated value for the day (using the same logic used during onboarding but restricted to the day window).
    • Compare the daily aggregated value with stored thresholds (lower and upper bounds) using metric ID mapping.
    • Insert daily result into DQ results, including primary method used. Note: primary method can change over time; method recalculation happens during periodic re-onboard (e.g., monthly) not on every daily run.
  • Implementation detail and code clarity Anand demonstrated code snippets (creating temporary base tables for mean, etc.) and recommended reusing those queries but parameterized for the daily window rather than re-reading artifacts. Team agreed: daily pipeline should read from DQ repository and execute parameterized aggregation queries; artifacts are not required at this stage. Samir/Athar to update daily code accordingly.
  • Confusion resolved Several participants confused artifacts vs DQ repo usage. Confirmed artifacts = UI staging only; DQ repository holds the canonical metric definitions and must be used for both daily checks and threshold mapping.
