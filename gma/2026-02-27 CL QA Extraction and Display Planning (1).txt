📒Meeting Outline

CL QA extraction & display

• Goal and high-level plan
  The core goal is to take an input CL (changelist) and find historical/matching CLs and related bugs, then surface QA notes so reviewers can decide testing needs. The plan is not finalized; current immediate objective is to fetch and display data (CL description, related bug(s), linked CLs, and QA notes) in a tabular view. Any automated reasoning (LLM/agent) on that data is planned as a later phase.

• Data sources and fields to collect
  Data to be collected: CL description, Buggnizer comments/QA notes, Bagnizer/Buggnizer notes/comments, and QA notes from linked CLs (the CLs attached to the bug). Previously the team collected CL description, Bagnizer comments/notes, and related CL numbers but did not fetch linked CL descriptions. Now the change requested is to also fetch QA notes for all related CLs attached to a bug.

• Scope: display vs decision-making
  Current deliverable: a Python script (not an agent) that iterates, fetches the CL → related bugs → linked CLs → QA notes, and renders the results in a tabular format in the front end. This view is for human QA reviewers to gain confidence. The system will not make final test-or-no-test decisions in phase 1. Using an LLM to make decisions (test suite selection, pass/fail, etc.) is a phase-2/phase-3 activity and requires explicit instructions/criteria from stakeholders.

Source & traversal logic

• Order of lookup and fallbacks
  Primary source: CL critic/excel sheet (CL description & CL-level QA notes). If CL-level QA notes are missing or unclear, team will check Buggnizer comments (bug-level QA notes). For a given input CL: find its bug(s); for each bug, enumerate linked CLs; for each linked CL, fetch QA notes (if present) from CL and Buggnizer. This aggregated information will be displayed.

• Use of linked CLs QA notes
  Team consensus: linked CL QA notes are useful to avoid missing test points and catch functionality that sits across multiple CLs. Even if the final automated reasoning will not use these notes in phase 1, fetching and displaying them adds value for manual reviewers.

• What will not be done yet
  No automated final decision-making (the system will not automatically mark a CL as "requires testing" or "do not test") in current phase. No detailed reasoning using linked CL QA as input to the decision engine in phase 1. Rack system architecture and agent-based workflows are out of scope for now.

Implementation details and next steps

• Implementation approach
  Implement a Python script that loops through inputs, calls critic/excel and Buggnizer endpoints, collects CL descriptions, related bug IDs, linked CL lists, and QA notes/comments, and produces a tabular display in the front end. The team will not modify existing rack architecture now; focus is on data fetch & display. Later, an LLM/agent can be added to consume the same data and provide suggested test cases or decide test-suites.

• Phase planning
  Phase 1: Data collection and tabular display of CL → bug → linked CLs → QA notes.  
  Phase 2 (planned): Use LLM/agent to suggest test suites and test cases or to take preliminary automated decisions; requires clear decision rules and acceptance criteria from stakeholders (examples: what constitutes "needs testing", how to map QA notes to test suites, priority rules).

• Testing & manual workflows
  The team clarified manual testing remains the primary execution method. Copycat/automation runs might exist for some CLs but are separate and not part of this CL-validation pipeline. The view produced will help manual QA to decide testing priorities. If production failures occur post-merge, manual reviewers investigate contract account issues and use historical CL/QA notes to identify missing checks.
