📒Meeting Outline

CL Verification process and purpose

• What is CL verification CL (Change List) verification is the QA process of validating code changes submitted via CLs. After a CL is submitted (e.g., Monday), QA verifies it in the following build (e.g., Tuesday) to ensure the change did not break existing functionality and any linked bug fixes are actually resolved.
• Primary goal The main objective is early detection of regressions caused by CLs so fixes or rollbacks can be performed before many dependent CLs pile up and make rollbacks complex.
• Verification scope QA primarily verifies that existing functionality is not broken by the CL (regression checks / sanity), and confirms bug fixes referenced by CLs. New feature verification (feature flag behaviour, full feature testing) is handled by the new-feature team, not by CL verification.
• When to test The team tests the latest build (the most recent certified build). CLs submitted between two certified builds (e.g., Jet C to Jet D) are extracted and considered; verification checks whether those CLs are live in the latest build and whether their intended fixes work without regressions.

Builds, bill types, servers and components

• Build categories and cadence

    • Fish build: hourly
    • Dog build: daily/weekly (weekly referenced)
    • Certified build: weekly
    • Release build: bi-weekly / promoted release Different bills (build types) have different generation frequencies and purposes.

• Servers and components Web, Android, and iOS have distinct servers and components. Extraction and verification processes differ by platform; Android and iOS are similar to each other in some respects but still have platform-specific components. Web has its own server naming (Pinto server referenced).

• Cross-platform CLs Backend CLs and mobile CLs can appear in the same dashboards. Web team flags CLs for mobile/backend that they cannot verify (marked as “behind the flag”) and forward those to the new-feature or mobile teams.

Extraction of CLs and tooling

• Current extraction approach Currently extraction is manual for web: QA provides previous and current certified build IDs (Jet C, Jet D) and runs scripts / tools to extract CLs submitted between those builds. Android has an automated script that uses APIs; the same endpoints could be re-used for web.

• Data captured Extracted data written to a spreadsheet includes: CL ID, CL description, QA note (if present), linked bug IDs, CL status (live/not live in a build), submission timestamps, server/build mappings.

• Dashboard and CL status The CL dashboard uses color indicators (green = live in build, red = not live). CL status and build URLs are available via the dashboard (Rapid referenced). CLs that are not live in the build (red) cannot be verified until they turn green.

• CL description and QA note CLs may include a QA note describing what to verify. If QA note absent, the QA looks for linked bugs or CL description to determine verification scope. If no QA note and no linked bug, a CL may be marked NA (not applicable) and not verified.

• Scripts / automation

    • Android: scripts exist using APIs to extract CLs, and some test cases are automated (pre-submit, copycat, post-submit).
    • Web: automation was intended but not fully implemented; manual work remains. The team discussed reusing Android endpoints/APIs to automate web CL extraction and populate spreadsheets.

Verification workflow and reporting

• Verification steps

    • Extract CLs between two certified builds (previous and current).
    • Check CL status (whether CL is live in the current build).
    • Read CL description and QA note; open linked bug(s).
    • Verify bug fix is present and functioning in the latest build and perform regression/sanity checks around impacted areas (exploratory testing for attachments, UI, dark theme where relevant).
    • If CL is not live, add comments to the CL or bug noting inability to verify and wait for green build.
    • If bug is not fixed, update bug and CL comments stating failure to verify.

• Failure handling If a CL causes a regression or a suspicious “culprit CL” is identified, the CL may be rolled back or a P0 patch may be deployed. For P0 fixes: do focused sanity/high-priority regression tests and sign off for the P0 promotion; full regression is usually not performed for emergency fixes.

• Status updates Verification status and notes are recorded in the bug system (not by changing CL status on the dashboard). QA posts “Working as intended” or failure details in the bug comment area and includes build references and screenshots where applicable.

Data, history and enhancements

• Historical data Historical extracts (spreadsheet history) for several years exist and were requested so agents can analyze patterns and feed automated decision logic.

• Enhancement opportunities

    • Automate web CL extraction using existing Android endpoints/APIs to reduce manual effort.
    • Provide a date-based extraction (select yesterday/today) to yield CLs for that day-stretch instead of manually supplying build IDs.
    • Filter CLs by presence of QA note or linked bugs to avoid unnecessary verification of NA CLs.
    • Pull linked bug details and attachments into spreadsheet to reduce navigation overhead.
    • Improve dashboard integration to flag which CLs require action by web QA vs. forwarded to other teams.
