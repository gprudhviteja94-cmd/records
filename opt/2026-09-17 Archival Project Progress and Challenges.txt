📒Meeting Outline

Archival Project Overview and Current Status

• Project Scope and Architecture  
  The archival project involves managing over 4 million archive files originally stored on NAS locations, now migrated to Azure Storage with metadata in MongoDB Atlas. The goal is to enable underwriters to search and download these archived files, which reside in an archive tier causing delayed availability (rehydration takes 5-6 hours). The system architecture includes backend applications deployed in AKS clusters that handle rehydration requests asynchronously via Azure Service Bus messaging.

• Backend and Frontend Responsibilities  
  The backend team is responsible for developing APIs that interact with Azure Service Bus and MongoDB to manage file requests, rehydration status, and notifications. The frontend will provide UI for underwriters to search files by name and request downloads. Authentication and user-specific views are planned but not yet implemented.

• Current Development Status  
  Backend APIs for interacting with Azure Service Bus and MongoDB are developed and deployed in AKS clusters. However, the archival API that will serve the frontend and handle authentication is still in the design phase. Frontend UI work has started but is incomplete; a large zipped UI package was shared but requires cleanup of Node.js modules to run locally.

Technical Challenges and Design Considerations

• File Search and Pagination  
  Searching 4+ million files by partial file name is a major challenge. The team discussed the need for efficient pagination and possibly caching some data on initial page load to avoid excessive MongoDB calls on every keystroke.

• Asynchronous Rehydration Workflow  
  The rehydration process is asynchronous and can take several hours. Initial API calls will provide synchronous acknowledgments, but the system must handle asynchronous notifications when files are ready. Currently, email notifications are sent to users when rehydration completes, but there is a requirement to also notify users via the UI.

• Azure Service Bus Messaging  
  The archival API acts as both a publisher (sending rehydration requests) and a consumer (receiving rehydration completion notifications) on Azure Service Bus topics. The team is exploring the best approach for implementing bi-directional communication with multiple topic subscriptions.

• Authentication and User Management  
  Authentication is planned to be handled at the archival API layer, not at the AKS cluster. The UI will be user-specific, showing dynamic download links and status based on logged-in user identity. Current authentication mechanisms are not yet implemented.

• Audit and Status Tracking  
  Metadata in MongoDB includes file details and rehydration status, along with a "waiters" list to track users who requested a file. Once rehydration completes and notifications are sent, the waiters list is cleared. This supports audit and status tracking.

• Integration and Dependencies  
  The archival API depends on the AKS cluster application to publish rehydration completion events. If this functionality is missing, the team will request its implementation. Coordination with Alok, who has implemented similar mechanisms in another project, is planned to gather best practices.

Next Steps and Coordination

  The frontend developer will review the shared UI package, clean up dependencies, and prepare a local environment to understand UI requirements. Discussions will continue to finalize API endpoints and data flows to support efficient search and asynchronous updates.

• Messaging and Event Handling Strategy  
  The team will explore multi-topic subscriptions on Azure Service Bus for bi-directional communication and confirm with AKS cluster owners about existing consumers and producers.
