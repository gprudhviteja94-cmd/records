📒Meeting Outline

Email download link security and desired behavior

• Current email behavior
  The backend generates an email that includes a direct storage URL (blob URL) with a SAS token. Clicking that email link opens a browser and starts an immediate download because the SAS token grants direct access. The link visible in the mail points to the storage account (block windows.net) and includes query parameters that act as the SAS token.

• Business concern
  Business flagged that sending direct download links (SAS URLs to blob storage) via email is a security/privacy concern — they prefer users to be routed to the application so authentication (SSO) occurs before any download. They want to avoid exposing direct storage links in email.

• Desired behavior
  From the email, users should be redirected to the application’s view-details page for the file (same UI the app shows when clicking "View details"). That page will then require SSO/authentication and present the download option only after the user is authenticated. The email should open the app view-details UI (possibly a popup or page) rather than triggering a direct SAS-based download.

• Clarifications on UI and flows
  The "view details" screen in the app currently shows file metadata; when the file is ready for download the UI may include a download button. There was discussion whether the view-details screen should include direct download or only a close button — consensus leaned toward routing users to the app where proper auth is applied before enabling download. The view-details display and the information passed to it are generated by the app; backend currently supplies the SAS-based download link, but the view-details modal/pop-up derives content from the app endpoints.

Technical constraints and responsibilities

• Who generates the email link
  The backend API constructs and sends the email and currently uses SAS-token-based links (generated per user but without user-bound authentication enforcement). The backend developer present confirmed they generate the SAS token based on user ID and append it to the storage path in the URL.

• Security implications of SAS tokens
  SAS URLs can allow anyone with the URL to download within the token lifetime if not tied to a strict authentication mechanism. The team observed that copying the link allowed another person to download, indicating the current implementation relies on time-limited SAS tokens but not per-request user authentication.

• Required changes
  Both backend and frontend changes are required:
  • Backend: stop embedding direct storage blob URLs in emails; instead construct a link pointing to the application (archival dev/opt-in or appropriate app base URL) and possibly a short link/redirect entry that maps to the app view-details endpoint.
  • Frontend: ensure the app can accept a link param to open the view-details page/modal for the referenced file and require SSO before exposing the download control.
  • Token behavior: preserve secure download mechanism (e.g., short-lived SAS tokens generated server-side only after the user authenticates), rather than pre-sharing a download SAS in email.

• Implementation options discussed
  • Replace the direct blob URL in email with an application URL that opens the view-details UI and triggers SSO if needed.
  • Keep SAS token usage but generate the SAS only after the user authenticates (i.e., on-demand SAS creation from a secured backend endpoint), or use a server-side proxy that requires auth and streams the file.
  • Option for creating short links/redirects that route to the app’s view-details page rather than the storage endpoint.

Action planning and next steps

• Evaluation and prototyping
  The backend developer will think through how to change link generation and what parameters must be passed to the app to recreate the view-details modal from an external link. They will review the frontend requirements (what data the view-details UI needs) to know what the email link should include (file identifier, request context) so the app can render the same view-details screen.

• Alignment and review
  The developer will propose changes and review them with the team the next day. Both backend and frontend teams must coordinate on the new link format, SSO flow, and secure SAS issuance (or alternative secure download mechanism).
