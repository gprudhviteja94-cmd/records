JSON Data Handling for RRF and New Requests

• Current JSON Storage and Retrieval  
  The discussion began with the JSON data stored for RPT and Satyam in blob storage. Ganesh will assist in providing the JSON currently stored for RPT and Satyam. The blob storage locations are maintained via environment variables, with two separate storages for given and Satyam data. Pawan was advised to refer to existing RRF code for these details.

• Mapping Fields for New RRF Requests  
  The team discussed the fields that need to be sent to the RPT team for new RRF requests. Since RPT and R have fewer values, mapping is straightforward. However, for new RRF requests, clarification is needed on which fields are mandatory. It was confirmed that fields such as client name, opportunity ID, and run date are important. Opportunity ID and client name are expected to be present, but run date may sometimes be empty or default to the current date. Pawan will receive copies of existing data for reference.

• Validation and Status for Sending JSON  
  The group discussed when the JSON should be sent to Satyam. It was clarified that the JSON should only be sent after the petrol process status is completed (ETL submitted status). This status check ensures the JSON is not sent prematurely or for every segment but at the entire quote ID and scenario level. George will be consulted in a future call to confirm the exact status and conditions for sending the JSON.

• Differences Between On-Prem and Modern RRF  
  It was noted that the on-prem RRF system already sends JSON to Satyam upon submission, but the modern RRF system does not currently do this. Ganesh will explain the on-prem logic to Pawan so that the same approach can be implemented for the modern RRF system.

• Ad Hoc Request Processing  
  The ad hoc JSON sending process is already completed and operational. The JSON is saved to two blob storages: one temporary and one for future use by Satyam. Pawan was encouraged to start working on the ad hoc requests immediately.
