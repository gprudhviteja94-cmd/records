📒Meeting Outline

File retrieval & token behavior

• Expired SAS token vs. file state
  Participants discussed confusion between an expired SAS token and the file being archived or in the cool tier. It was clarified: file can be in the cool tier (readily downloadable) while the SAS token previously issued for download has expired. The UI currently labels these as "download expired" which refers to token expiry, not file expiry.
• User expectation when token expired
  The customer expects that when they click "request again" (or re-request the SAS token) the download should start immediately if the file itself is already available (e.g., in cool tier). Current behavior often requires navigation back to Find Files or My Requests for the download to appear available, which is inconsistent and confusing.

UI behavior & messaging inconsistencies

• In-page status updates
  The group reviewed that when a user re-requests a token for a file already in cool tier, the same page should dynamically show that the file is available and present download options immediately. Currently the status does not consistently refresh in-place, forcing users to navigate away and search again to see the file marked available.
• "Restore request" vs "request again" wording
  The term "restore request" and other messaging (e.g., "restore already in progress", "request expired") is misleading in several contexts. Restore implies archival rehydration; however in many cases only the SAS token expired and re-requesting should simply regenerate the token and allow immediate download. Participants recommended clearer, accurate messaging for token vs. archive/rehydration cases.
• Misleading temporary-copy prompts
  There is a UI prompt about "temporary copy will be created" appearing for files that are in cool tier (i.e., do not require rehydration). This is misleading and creates unnecessary concern for users — it should not appear when only a token re-issue is needed.

Backend / token logic & expiration window

• SAS token expiration logic
  Participants reviewed token lifetime logic: previously 15 minutes, now changed to a 7-day validity for SAS tokens. The UI derives the displayed expiry date range from the token metadata (example: Oct 6 to Oct 13). The computation for showing "download expired" is aligned with SAS token timestamps.
• How system detects expired token
  The backend uses the SAS token expiry timestamp stored in metadata (MongoDB) to decide whether to mark a request as expired. This was explained and accepted as correct.
• Performance considerations when searching
  There was a brief discussion about search latency when fetching file/request entries from MongoDB. Current implementation uses pagination and no caching. Occasional delays were observed pulling metadata; participants considered whether intermediate caching would help but noted pagination prevents loading all entries at once.

Repro steps / observed inconsistencies

• Reproduction flow observed in meeting
  The participant demonstrated searching for a filename which returned two entries: one archived (needs rehydration) and one in cool tier (ready). For the same file the "My Requests" view showed "download expired" and presented a "request again" action. After clicking "request again" the download did not start automatically on that page; however, after navigating back to Find Files and searching again, the file showed as available and secure download could be started.
• Inconsistent UI states across pages
  The same file shows different actionable states depending on whether it is viewed in Find Files vs My Requests. This inconsistency is a core frustration.

Prioritization & next steps discussed

• Confirmed three primary UI issues to address:
  1) Re-requesting a token for a file already in cool tier should trigger immediate download without needing navigation.
  2) Remove or suppress misleading "temporary copy will be created" prompt when only SAS token regeneration is required.
  3) Fix confusing messages such as "restore request" or "request already submitted" for token-expiry cases; show clear guidance (e.g., "SAS token expired — request new token" and then allow direct download).
• Backend note: SAS token lifetime change to 7 days acknowledged; UI should reflect and use token metadata correctly.
