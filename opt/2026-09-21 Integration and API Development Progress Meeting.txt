📒Meeting Outline

Integration and API Development Progress

• Rehydration Process and Worker API  
  The rehydration process is managed by the CI system, which completes the process and sends notification emails. Two applications are connected via Azure Service Bus: a front-end app and a back-end worker API. The worker API is already developed and deployed in AKS clusters. A white paper detailing the worker API’s request/response contract and sample data was shared for reference.

• Current Development Status and GitHub Repository  
  Front-end development is progressing with test data inserted into MongoDB collections. The API development is complete, but the GitHub repository for the new API has not yet been created, blocking code commits and integration testing. Once the repo is ready, full validation of API connectivity and functionality can proceed.

UI and Backend Data Handling

• UI Functionality and MongoDB Schema  
  The front-end UI allows users to search files, submit restore requests with reasons, and view request statuses. MongoDB collections store user requests and metadata with some schema differences noted (e.g., additional fields like business reason and retention hours). Pagination and sorting by last updated date are planned for efficient data display.

• API and UI Integration Details  
  The UI is connected to the local back-end, enabling file search and request submission. Currently, all records are fetched without limits, which needs optimization. The UI shows a single "Request Restore" button per file, which triggers the backend API to check the file’s current archive status and either initiate rehydration or generate a download token.

Token Management and Download Process

• Token Generation and User-Specific Access  
  Tokens for downloading files are generated per user and file combination, valid for 48 hours. This approach ensures secure, user-specific access and supports future authorization enhancements. The backend checks if a file is already rehydrated before generating a token, avoiding redundant rehydration requests.

• Download Link and UI Behavior  
  The UI should not display download links unless the file is confirmed to be rehydrated. Instead, a single "Request Restore" button is shown, which either returns a download link immediately if the file is ready or confirms that the request for rehydration is accepted. This simplifies the UI and avoids confusion from stale or inaccurate status displays.

Data Synchronization and UI Refresh Challenges

• Sync Between MongoDB and UI  
  A key challenge is keeping the UI in sync with the backend MongoDB data, especially since file status changes (archive to cool tier and vice versa) can happen asynchronously and take hours. Live status updates are difficult due to caching and the large volume of data (~400,000+ records).

• Proposed UI Refresh Strategies  
  Suggestions include a manual refresh button on the UI and periodic refreshes to update file statuses. However, frequent automatic refreshes could add complexity and performance overhead. The team agreed on a simpler approach: show the latest status on page load and after user actions, and prompt users to resubmit requests if the file status changes unexpectedly.

Future Considerations and Security

• Multiple Storage Tiers and Use Cases  
  The system may need to support multiple archive tiers and different data sources (e.g., NAS files, on-prem SQL data) in the future. The architecture should be flexible to handle such expansions.

• SSO and User Roles  
  Single Sign-On (SSO) integration is planned for the UI to ensure secure access. Currently, only one user role is defined, allowing all logged-in users to view, request, and download files. Role-based access control may be introduced later to segregate users by business type or permissions.

• Testing and Deployment Plans  
  Manual validation will be prioritized before implementing automated testing (e.g., Playwright scripts). Once the GitHub repo is created and code is pushed, deployment and live data testing will proceed.
