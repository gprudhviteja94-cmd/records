📒Meeting Outline

Migration Context and Overview

• Purpose and Background of Migration  
  The meeting clarified the ongoing migration from Composer (version 2.x) to Astronomer (Airflow 3) on the Lumi platform due to Composer 2.x reaching end-of-life by December 2026. Users must upgrade to Composer 3 and eventually migrate to Astronomer for better performance, operational efficiency, security, and financial benefits. The migration is a leadership-driven decision following a successful POC by Lumi core platform and cloud engineering teams.

• User Impact and Communication  
  Notifications and materials have been shared multiple times, including recordings and a Slack channel for questions. The migration affects projects currently using Composer, but some users (e.g., from accounting or CFR teams) were unsure if it applies to them, highlighting the need for clearer communication and project applicability checks.

• Migration Options and Recommendations  
  Two options exist:  
  1. Direct migration from Composer 2.x to Astronomer (recommended for phase one and two users).  
  2. A two-step upgrade: Composer 2.x to Composer 3 by end of 2026, then to Airflow 3 in 2027 (option for phase three users with exceptions).  
  Phase three users needing delay must provide business justification and get director approval.

Migration Phases, Timelines, and Process

• Phases and Deadlines  
  • Phase one started June 9, 2026, with a target completion by August 17, 2026.  
  • Phase two to be completed by end of October 2026.  
  • Phase three expected to complete by end of Q1 2027, with flexible start dates.  
  Users can request phase changes (e.g., moving from phase three to two) based on resource availability.

• Project Tracking and Access  
  A project tracker is maintained and shared via SharePoint with access managed on request. Users are encouraged to update required fields in the tracker to facilitate migration scheduling.

• Migration Execution and Validation  
  For E1 environment, Lumi core team migrates and makes tags Airflow 3 compatible, uploads them to Astronomer deployment and GCS bucket for users to validate. Users test and sign off within about a week before moving to higher environments (E2, E3). Support is provided via Slack channel for issues during validation.

• Deployment and CI/CD Process  
  Migration involves moving DAGs and related tag code from Composer’s GCS buckets to Git repositories integrated with Astronomer deployments using CI/CD pipelines. A template for GitHub Actions is provided and extended to support Astronomer without conflicting with existing deployment processes.

Technical Details and User Responsibilities

• Code and Compatibility Changes  
  Migration requires making tags compatible with Airflow 3 syntax changes; however, no changes are made to business logic or non-Python code. Only Python tag code is affected. Users may need to adjust code if breaking changes affect their logic.

• Support for Custom Operators and SDK  
  Custom operators are not automatically migrated; users must handle these manually. Lumi SDK and Griffin integrations are packaged and installed in Astronomer, removing dependency on GCS buckets for these components.

• Data Flow and Java Operator Concerns  
  The move away from Dataflow Java operator to flex templates is recommended due to stability and performance issues; this best practice continues in Astronomer.

• Coexistence of Composer and Astronomer  
  Both Composer (Airflow 2) and Astronomer (Airflow 3) can coexist during migration phases to avoid disruption. Once sign-off is given on E3, Composer instances will be decommissioned.

• Downtime and History Migration  
  No downtime is expected during migration. Composer DAG run history is not migrated by default; if required, it needs business justification and may cause downtime.

• Resource and Performance Considerations  
  Users experiencing slowness or queuing in preprod environments can raise issues for investigation. Potential worker scaling during migration can be discussed.
