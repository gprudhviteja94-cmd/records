## 📒Meeting Outline

### Batch Template API Development and Alignment with Batch Payment Flow

* **Current Progress and Similarity to Batch Payment Flow**\
  The batch template creation flow is intended to closely mirror the batch payment creation flow, especially in how batches are created and managed. The main difference is the inclusion of additional fields in the template, such as "allow edits." However, no significant progress has been made beyond initial implementation of "allow edits" and basic save and submit functionalities. The team has not yet reviewed complaint handling or entitlement checks.

* **Request and Response Structure Consistency**\
  Recent changes in the batch payment API responses (to align with ITC standards) necessitate similar updates for the batch template APIs to maintain consistency. The current template API responses have not been documented yet, and it was agreed that the team will update Confluence with the current state and align the template API responses with batch payment responses.

* **Endpoint Design and Backward Compatibility**\
  There was a discussion about whether to create new endpoints for batch templates or reuse existing single template endpoints with toggles. The consensus leaned towards creating separate endpoints or branching logic within the same endpoint to avoid breaking existing BAU (Business As Usual) flows. The product code should be derived from the actual request fields rather than path variables to ensure correctness.

* **Validation and Entitlement Checks**\
  The batch template flow currently lacks entitlement checks and some validations present in the BAU single template flow. It was emphasized that entitlement and validation logic from the BAU flow must be reviewed, understood, and incorporated appropriately into the batch template flow to avoid gaps. Some validations like limits may not apply to templates, but entitlement checks definitely should.

* **Database and Persistence Layer Details**\
  The batch template data is persisted in new tables: Template, Template Benny (beneficiary), and Template Party. The aggregated amount and total beneficiary count are not currently updated in the template table but should be included. The "allow edit" configuration is stored at the beneficiary level with a restriction column indicating editable fields. The exact database table relationships and how these restrictions map to templates need further clarification and examples.

* **Reuse of Existing BAU Logic and Code**\
  There is potential to reuse existing BAU validation and business logic by mapping the batch template request payload to existing entity structures temporarily for validation purposes, while persisting data in the new template tables. This approach requires careful analysis to avoid breaking existing flows.

* **Parallel Development and Story Creation for Next Sprint**\
  It was agreed to split the batch template development into parallel workstreams: save and submit, get beneficiary list API, and modify payment wrapper equivalent for templates. The team will create detailed user stories for these tasks for the next sprint, reusing existing high-level stories where applicable and creating new ones as needed.

* **Integration with UI and Coordination with Frontend Team**\
  The backend APIs for batch templates should align with the UI flows already documented by the Photon team. The team will coordinate with frontend leads (Kuver and Jagan) to understand the UI flow and required API calls, ensuring the batch template APIs support similar user experiences as batch payments.

* **Staging and Drawer Functionality**\
  The staging tables and drawer UI components used in batch payments will be reused for templates with minimal changes. The drawer modification API for individual payments has an equivalent planned for templates.

* **IPDL and Remittance Considerations**\
  IPDL (India Payment Data Layer) integration is pending and will be addressed in the next sprint. Remittance functionality is not applicable to templates and is only relevant for payments.

### Documentation and Knowledge Sharing

* **Confluence Updates and Documentation**\
  The team will update Confluence with API request and response structures for batch templates, similar to the batch payment documentation. This will aid in review and integration by the Photon team.

* **Code Review and PR Management**\
  Ongoing PRs related to batch payment and template flows will be reviewed carefully to ensure consistent implementation and avoid breaking changes.
